이 가이드는 ES 모듈이 무엇인지와 Nuxt 앱(또는 상위 라이브러리)을 ESM과 호환되게 만드는 방법을 설명합니다.

## 배경 %{#background}%

### CommonJS 모듈 %{#commonjs-modules}%

CommonJS(CJS)는 격리된 JavaScript 모듈 간에 기능을 공유할 수 있도록 Node.js가 도입한 형식입니다([더 읽어보기](https://nodejs.org/api/modules.html)).
아마 다음과 같은 문법에 이미 익숙하실 것입니다:

```js
const a = require('./a')

module.exports.a = a
```

webpack과 Rollup 같은 번들러는 이 문법을 지원하며 브라우저에서 CommonJS로 작성된 모듈을 사용할 수 있게 해줍니다.

### ESM 문법 %{#esm-syntax}%

대부분 ESM과 CJS를 비교해서 말할 때는 [모듈](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules)을 작성하는 서로 다른 문법을 가리킵니다.

```js
import a from './a'

export { a }
```

ECMAScript 모듈(ESM)이 표준이 되기 전까지는(무려 10년이 넘게 걸렸습니다!) [webpack](https://webpack.js.org/guides/ecma-script-modules/) 같은
도구와 TypeScript 같은 언어가 이른바 **ESM 문법**을 먼저 지원하기 시작했습니다.
하지만 실제 명세와는 몇 가지 중요한 차이가 있으며, 이에 대해서는 [이 설명 글](https://hacks.mozilla.org/2018/03/es-modules-a-cartoon-deep-dive/)이 도움이 됩니다.

### '네이티브' ESM이란? %{#what-is-native-esm}%

여러분은 이미 오랫동안 ESM 문법으로 앱을 작성해 왔을 수 있습니다. 결국 브라우저는 이를 네이티브로 지원하고, Nuxt 2에서는 작성한 모든 코드를 알맞은 형식(서버용 CJS, 브라우저용 ESM)으로 컴파일해 주었습니다.

패키지에 모듈을 추가할 때는 상황이 조금 달랐습니다. 예를 들어 어떤 라이브러리는 CJS 버전과 ESM 버전을 모두 노출해 두고, 우리가 원하는 쪽을 고를 수 있게 했습니다:

```json
{
  "name": "sample-library",
  "main": "dist/sample-library.cjs.js",
  "module": "dist/sample-library.esm.js"
}
```

그래서 Nuxt 2에서는 번들러(webpack)가 서버 빌드에는 CJS 파일(`main`)을 가져오고, 클라이언트 빌드에는 ESM 파일(`module`)을 사용했습니다.

::note
`module` 필드는 webpack과 Rollup 같은 번들러가 사용하는 관례이지만, Node.js 자체는 이를 인식하지 않습니다. Node.js는 모듈 해석 시 [`exports`](https://nodejs.org/api/packages.html#exports)와 [`main`](https://nodejs.org/api/packages.html#main) 필드만 사용합니다.
::

하지만 최근 Node.js LTS 릴리스에서는 이제 Node.js 안에서 [네이티브 ESM 모듈을 사용할 수 있습니다](https://nodejs.org/api/esm.html). 즉, 기본 동작은 아니더라도 Node.js 자체가 ESM 문법을 사용하는 JavaScript를 처리할 수 있다는 뜻입니다. ESM 문법을 활성화하는 가장 일반적인 두 가지 방법은 다음과 같습니다:

- `package.json` 안에 `"type": "module"`을 설정하고 `.js` 확장자를 계속 사용하기
- `.mjs` 파일 확장자를 사용하기(권장)

Nuxt Nitro가 바로 이 방식을 사용하며, `.output/server/index.mjs` 파일을 출력합니다. 이는 Node.js에게 이 파일을 네이티브 ES 모듈로 취급하라고 알려줍니다.

### Node.js 환경에서 유효한 import는 무엇인가요? %{#what-are-valid-imports-in-a-node-js-context}%

모듈을 `require`하는 대신 `import`하면 Node.js는 이를 다르게 해석합니다. 예를 들어 `sample-library`를 import하면 Node.js는 해당 라이브러리의 `package.json`에서 `exports` 항목을 찾고, `exports`가 정의되어 있지 않으면 `main` 항목으로 되돌아갑니다.

이는 `const b = await import('sample-library')`와 같은 동적 import에도 동일하게 적용됩니다.

Node는 다음과 같은 종류의 import를 지원합니다([문서 보기](https://nodejs.org/api/packages.html#determining-module-system)):

1. `.mjs`로 끝나는 파일 - ESM 문법을 사용할 것으로 기대됩니다
1. `.cjs`로 끝나는 파일 - CJS 문법을 사용할 것으로 기대됩니다
1. `.js`로 끝나는 파일 - 해당 `package.json`에 `"type": "module"`이 없는 한 CJS 문법을 사용할 것으로 기대됩니다

### 어떤 문제가 발생할 수 있나요? %{#what-kinds-of-problems-can-there-be}%

오랫동안 모듈 작성자들은 ESM 문법으로 빌드한 결과물을 `.esm.js`나 `.es.js` 같은 관례적 이름으로 만들고, 이를 `package.json`의 `module` 필드에 추가해 왔습니다. 지금까지는 이런 파일이 확장자를 크게 신경 쓰지 않는 webpack 같은 번들러에서만 사용됐기 때문에 문제가 되지 않았습니다.

하지만 Node.js의 ESM 환경에서 `.esm.js` 파일을 가진 패키지를 import하려고 하면 동작하지 않으며, 다음과 같은 오류를 보게 됩니다:

```bash [Terminal]
(node:22145) Warning: To load an ES module, set "type": "module" in the package.json or use the .mjs extension.
/path/to/index.js:1

export default {}
^^^^^^

SyntaxError: Unexpected token 'export'
    at wrapSafe (internal/modules/cjs/loader.js:1001:16)
    at Module._compile (internal/modules/cjs/loader.js:1049:27)
    at Object.Module._extensions..js (internal/modules/cjs/loader.js:1114:10)
    ....
    at async Object.loadESM (internal/process/esm_loader.js:68:5)
```

Node.js가 CJS라고 판단한 ESM 문법 빌드에서 이름 있는 import를 가져올 때도 다음과 같은 오류가 발생할 수 있습니다:

```bash [Terminal]
file:///path/to/index.mjs:5
import { named } from 'sample-library'
         ^^^^^
SyntaxError: Named export 'named' not found. The requested module 'sample-library' is a CommonJS module, which may not support all module.exports as named exports.

CommonJS modules can always be imported via the default export, for example using:

import pkg from 'sample-library';
const { named } = pkg;

    at ModuleJob._instantiate (internal/modules/esm/module_job.js:120:21)
    at async ModuleJob.run (internal/modules/esm/module_job.js:165:5)
    at async Loader.import (internal/modules/esm/loader.js:177:24)
    at async Object.loadESM (internal/process/esm_loader.js:68:5)
```

## ESM 문제 해결 %{#troubleshooting-esm-issues}%

이런 오류를 마주쳤다면 문제는 거의 확실하게 상위 라이브러리에 있습니다. 해당 라이브러리에서 Node가 import할 수 있도록 [라이브러리를 수정해야 합니다](/docs/4.x/guide/concepts/esm#library-author-guide).

### 라이브러리 트랜스파일 %{#transpiling-libraries}%

그동안은 이 라이브러리들을 `build.transpile`에 추가하여 Nuxt가 직접 import하려 하지 않도록 만들 수 있습니다:

```ts twoslash
export default defineNuxtConfig({
  build: {
    transpile: ['sample-library'],
  },
})
```

이 라이브러리들이 import하는 다른 패키지도 _함께_ 추가해야 하는 경우가 있을 수 있습니다.

### 라이브러리 별칭 지정 %{#aliasing-libraries}%

경우에 따라서는 라이브러리를 CJS 버전으로 수동 별칭 지정해야 할 수도 있습니다. 예를 들면 다음과 같습니다:

```ts twoslash
export default defineNuxtConfig({
  alias: {
    'sample-library': 'sample-library/dist/sample-library.cjs.js',
  },
})
```

### 기본 export %{#default-exports}%

CommonJS 형식의 의존성은 `module.exports`나 `exports`를 사용해 기본 export를 제공할 수 있습니다:

```js [node_modules/cjs-pkg/index.js]
module.exports = { test: 123 }
// or
exports.test = 123
```

이런 의존성을 `require`할 때는 보통 잘 동작합니다:

```js [test.cjs]
const pkg = require('cjs-pkg')

console.log(pkg) // { test: 123 }
```

[네이티브 ESM 모드의 Node.js](https://nodejs.org/api/esm.html#interoperability-with-commonjs), [`esModuleInterop`가 활성화된 TypeScript](https://www.typescriptlang.org/tsconfig/#esModuleInterop), 그리고 webpack 같은 번들러는 이런 라이브러리를 기본 import할 수 있도록 호환 메커니즘을 제공합니다.
이 메커니즘은 흔히 "interop require default"라고 불립니다:

```js
import pkg from 'cjs-pkg'

console.log(pkg) // { test: 123 }
```

하지만 문법 감지와 서로 다른 번들 형식의 복잡성 때문에 interop default가 실패하여 다음과 같은 결과가 나올 가능성은 언제나 있습니다:

```js
import pkg from 'cjs-pkg'

console.log(pkg) // { default: { test: 123 } }
```

또한 동적 import 문법을 사용할 때는(CJS 파일과 ESM 파일 모두에서) 항상 다음과 같은 상황이 생깁니다:

```js
import('cjs-pkg').then(console.log) // [Module: null prototype] { default: { test: '123' } }
```

이 경우에는 기본 export를 수동으로 interop해야 합니다:

<!-- eslint-disable import/no-named-default -->

```js
// Static import
import { default as pkg } from 'cjs-pkg'

// Dynamic import
import('cjs-pkg').then(m => m.default || m).then(console.log)
```

더 복잡한 상황을 더 안전하게 처리하기 위해, Nuxt에서는 이름 있는 export를 유지할 수 있는 [mlly](https://github.com/unjs/mlly)의 사용을 권장하며 내부적으로도 사용합니다.

```js
import { interopDefault } from 'mlly'

// Assuming the shape is { default: { foo: 'bar' }, baz: 'qux' }
import myModule from 'my-module'

console.log(interopDefault(myModule)) // { foo: 'bar', baz: 'qux' }
```

## 라이브러리 작성자 가이드 %{#library-author-guide}%

좋은 소식은 ESM 호환성 문제를 비교적 간단하게 해결할 수 있다는 점입니다. 주요 방법은 두 가지입니다:

1. **ESM 파일 이름을 `.mjs`로 끝나게 바꿀 수 있습니다.**

   _이것이 가장 권장되며 가장 단순한 접근 방식입니다._ 라이브러리의 의존성이나 빌드 시스템과 관련된 문제를 정리해야 할 수 있지만, 대부분의 경우 이것만으로 문제가 해결됩니다. 명확성을 높이기 위해 CJS 파일도 `.cjs`로 끝나게 이름을 바꾸는 것이 좋습니다.

1. **라이브러리 전체를 ESM 전용으로 만들 수도 있습니다**.

   이는 `package.json`에 `"type": "module"`을 설정하고 빌드된 라이브러리가 ESM 문법을 사용하도록 보장하는 것을 의미합니다. 하지만 의존성과 관련된 문제가 발생할 수 있으며, 이 접근 방식은 라이브러리를 ESM 환경에서만 _소비할 수 있게_ 만든다는 뜻이기도 합니다.

### 마이그레이션 %{#migration}%

CJS에서 ESM으로 넘어가는 첫 단계는 `require` 사용 부분을 `import`로 바꾸는 것입니다:

::code-group

```ts [Before]
module.exports = function () { /* ... */ }

exports.hello = 'world'
```

```ts [After]
export default function () { /* ... */ }

export const hello = 'world'
```

::

::code-group

```js [Before]
const myLib = require('my-lib')
```

```js [After]
import myLib from 'my-lib'
// or
const dynamicMyLib = await import('my-lib').then(lib => lib.default || lib)
```

::

ESM 모듈에서는 CJS와 달리 `require`, `require.resolve`, `__filename`, `__dirname` 전역 변수를 사용할 수 없으며
`import()`와 `import.meta.filename`으로 대체해야 합니다.

::code-group

```js [Before]
const { join } = require('node:path')

const newDir = join(__dirname, 'new-dir')
```

```js [After]
import { fileURLToPath } from 'node:url'

const newDir = fileURLToPath(new URL('./new-dir', import.meta.url))
```

::

::code-group

```js [Before]
const someFile = require.resolve('./lib/foo.js')
```

```js [After]
import { resolvePath } from 'mlly'

const someFile = await resolvePath('my-lib', { url: import.meta.url })
```

::

### 모범 사례 %{#best-practices}%

- 기본 export보다 이름 있는 export를 선호하세요. 이렇게 하면 CJS 충돌을 줄이는 데 도움이 됩니다. ([기본 export](/docs/4.x/guide/concepts/esm#default-exports) 섹션 참고)

- Nitro polyfill 없이도 브라우저와 Edge Worker에서 라이브러리를 사용할 수 있도록, Node.js 내장 모듈과 CommonJS 또는 Node.js 전용 의존성에 대한 의존을 가능한 한 피하세요.

- 조건부 export와 함께 새로운 `exports` 필드를 사용하세요. ([더 읽어보기](https://nodejs.org/api/packages.html#conditional-exports)).

```json
{
  "exports": {
    ".": {
      "import": "./dist/mymodule.mjs"
    }
  }
}
```
