이 장의 목표는 프레임워크를 구성하는 여러 부분, 그 실행 순서, 그리고 이들이 함께 동작하는 방식을 높은 수준에서 개괄하는 것입니다.

## 서버 라이프사이클 %{#server-lifecycle}%

서버에서는 애플리케이션에 대한 각 초기 요청마다 다음 단계가 실행됩니다.

::steps
### 서버 플러그인 :badge[once]{color="info" class="align-middle"} %{#server-plugins}%

Nuxt는 최신 서버 엔진인 [Nitro](https://nitro.build/)로 구동됩니다.

Nitro가 시작되면 [`/server/plugins`](/docs/4.x/directory-structure/server#server-plugins) 디렉터리 아래의 플러그인을 초기화하고 실행합니다. 이 플러그인은 다음을 수행할 수 있습니다.
- 애플리케이션 전역 오류를 포착하고 처리합니다.
- Nitro가 종료될 때 실행되는 훅을 등록합니다.
- 응답 수정과 같은 요청 라이프사이클 이벤트용 훅을 등록합니다.

::callout{icon="i-lucide-lightbulb"}
Nitro 플러그인은 서버가 시작될 때 단 한 번만 실행됩니다. 서버리스 환경에서는 들어오는 각 요청마다 서버가 부팅되며 Nitro 플러그인도 함께 부팅됩니다. 다만 이 플러그인들은 await되지 않습니다.
::

:read-more{to="/docs/4.x/directory-structure/server#server-plugins"}

### 서버 미들웨어 %{#server-middleware}%

Nitro 서버를 초기화한 뒤에는 `server/middleware/` 아래의 미들웨어가 모든 요청마다 실행됩니다. 미들웨어는 인증, 로깅, 요청 변환과 같은 작업에 사용할 수 있습니다.

::warning
미들웨어에서 값을 반환하면 요청이 종료되고 반환된 값이 응답으로 전송됩니다. 올바른 요청 처리를 위해 이 동작은 일반적으로 피해야 합니다!
::

:read-more{to="/docs/4.x/directory-structure/server#server-middleware"}

### 앱 플러그인 %{#app-plugins}%

먼저 Vue와 Nuxt 인스턴스가 생성됩니다. 그 후 Nuxt가 앱 플러그인을 실행합니다. 여기에는 다음이 포함됩니다.
- Vue Router와 `unhead` 같은 내장 플러그인
- `app/plugins/` 디렉터리에 있는 사용자 정의 플러그인으로, 접미사가 없는 것(예: `myPlugin.ts`)과 `.server` 접미사가 있는 것(예: `myServerPlugin.server.ts`)을 포함합니다.

플러그인은 특정한 순서로 실행되며 서로 의존성을 가질 수 있습니다. 실행 순서와 병렬 실행을 포함한 자세한 내용은 [플러그인 문서](/docs/4.x/directory-structure/app/plugins)를 참고하세요.

::callout{icon="i-lucide-lightbulb"}
이 단계 이후 Nuxt는 [`app:created`](/docs/4.x/api/advanced/hooks#app-hooks-runtime) 훅을 호출하며, 이를 사용해 추가 로직을 실행할 수 있습니다.
::

:read-more{to="/docs/4.x/directory-structure/app/plugins"}

### 라우트 검증 %{#route-validation}%

플러그인을 초기화한 뒤이자 미들웨어를 실행하기 전, `definePageMeta` 함수에 `validate` 메서드가 정의되어 있으면 Nuxt가 이를 호출합니다. `validate` 메서드는 동기식일 수도 비동기식일 수도 있으며, 동적 라우트 매개변수를 검증하는 데 자주 사용됩니다.

- 매개변수가 유효하면 `validate` 함수는 `true`를 반환해야 합니다.
- 검증에 실패하면 `false` 또는 `status` 및/또는 `statusText`를 포함한 객체를 반환하여 요청을 종료해야 합니다.

자세한 내용은 [라우트 검증 문서](/docs/4.x/getting-started/routing#route-validation)를 참고하세요.

:read-more{to="/docs/4.x/getting-started/routing#route-validation"}

### 앱 미들웨어 %{#app-middleware}%

미들웨어를 사용하면 특정 라우트로 이동하기 전에 코드를 실행할 수 있습니다. 인증, 리디렉션, 로깅과 같은 작업에 자주 사용됩니다.

Nuxt에는 세 가지 유형의 미들웨어가 있습니다.
- **전역 라우트 미들웨어**
- **이름 있는 라우트 미들웨어**
- **익명(또는 인라인) 라우트 미들웨어**

Nuxt는 초기 페이지 로드 시(서버와 클라이언트 모두) 모든 전역 미들웨어를 실행하고, 이후 각 클라이언트 측 내비게이션 전에 다시 실행합니다. 이름 있는 미들웨어와 익명 미들웨어는 해당 페이지 컴포넌트에 정의된 페이지(라우트) 메타의 middleware 속성에 지정된 라우트에서만 실행됩니다.

각 유형의 세부 사항과 예시는 [미들웨어 문서](/docs/4.x/directory-structure/app/middleware)를 참고하세요.

서버에서 발생하는 모든 리디렉션은 브라우저에 `Location:` 헤더를 전송하게 되며, 브라우저는 이 새 위치로 새로운 요청을 보냅니다. 이때 쿠키에 상태를 유지하지 않았다면 애플리케이션 상태는 모두 초기화됩니다.

:read-more{to="/docs/4.x/directory-structure/app/middleware"}

### 페이지와 컴포넌트 %{#page-and-components}%

이 단계에서 Nuxt는 페이지와 그 컴포넌트를 렌더링하고 `useFetch`와 `useAsyncData`로 필요한 데이터를 가져옵니다. 서버에서는 동적 업데이트도 없고 DOM 작업도 발생하지 않기 때문에 `onBeforeMount`, `onMounted` 및 그 이후의 Vue 라이프사이클 훅은 SSR 중에 **실행되지 않습니다**.

기본적으로 Vue는 더 나은 성능을 위해 SSR 중 의존성 추적을 일시 중지합니다.

::callout{icon="i-lucide-lightbulb"}
서버 측에는 반응성이 없습니다. Vue SSR은 앱을 위에서 아래로 정적 HTML로 렌더링하므로, 이미 렌더링된 콘텐츠를 다시 돌아가 수정하는 것이 불가능하기 때문입니다.
::

::important
`<script setup>`의 루트 스코프에서 정리가 필요한 부수 효과를 만드는 코드는 피해야 합니다. 이런 부수 효과의 예로는 `setInterval`로 타이머를 설정하는 것이 있습니다. 클라이언트 전용 코드에서는 타이머를 설정한 뒤 `onBeforeUnmount`나 `onUnmounted`에서 해제할 수 있습니다. 하지만 SSR 중에는 unmount 훅이 결코 호출되지 않으므로 타이머가 영원히 남게 됩니다. 이를 피하려면 이런 부수 효과 코드를 `onMounted` 안으로 옮기세요.
::

::tip{icon="i-lucide-video" to="https://youtu.be/dZSNW07sO-A" target="_blank"}
Daniel Roe가 서버 렌더링과 전역 상태를 설명하는 영상을 시청해 보세요.
::

### HTML 출력 %{#html-output}%

필요한 데이터를 모두 가져오고 컴포넌트 렌더링이 끝나면, Nuxt는 렌더링된 컴포넌트를 `unhead` 설정과 결합해 완전한 HTML 문서를 생성합니다. 그런 다음 이 HTML과 관련 데이터를 클라이언트로 다시 보내 SSR 과정을 완료합니다.

::callout{icon="i-lucide-lightbulb"}
Vue 애플리케이션을 HTML로 렌더링한 뒤 Nuxt는 [`app:rendered`](/docs/4.x/api/advanced/hooks#app-hooks-runtime) 훅을 호출합니다.
::

::callout{icon="i-lucide-lightbulb"}
HTML을 최종 확정해 전송하기 전에 Nitro는 [`render:html`](/docs/4.x/api/advanced/hooks#nitro-app-hooks-runtime-server-side) 훅을 호출합니다. 이 훅을 사용하면 추가 스크립트를 삽입하거나 메타 태그를 수정하는 등 생성된 HTML을 조작할 수 있습니다.
::

::

## 클라이언트 라이프사이클 %{#client-lifecycle}%

라이프사이클의 이 부분은 어떤 Nuxt 모드를 선택했는지와 관계없이 브라우저에서 완전히 실행됩니다.

::steps

### 앱 플러그인 %{#app-plugins}%

이 단계는 서버 측 실행과 비슷하며, 내장 플러그인과 사용자 정의 플러그인을 모두 포함합니다.

`app/plugins/` 디렉터리에 있는 사용자 정의 플러그인 중 접미사가 없는 것(예: `myPlugin.ts`)과 `.client` 접미사가 있는 것(예: `myClientPlugin.client.ts`)은 클라이언트 측에서 실행됩니다.

::callout{icon="i-lucide-lightbulb"}
이 단계 이후 Nuxt는 [`app:created`](/docs/4.x/api/advanced/hooks#app-hooks-runtime) 훅을 호출하며, 이를 사용해 추가 로직을 실행할 수 있습니다.
::

:read-more{to="/docs/4.x/directory-structure/app/plugins"}

### 라우트 검증 %{#route-validation}%

이 단계는 서버 측 실행과 동일하며, `definePageMeta` 함수에 정의되어 있다면 `validate` 메서드를 포함합니다.

### 앱 미들웨어 %{#app-middleware}%

Nuxt 미들웨어는 서버와 클라이언트 모두에서 실행됩니다. 특정 환경에서만 실행되어야 하는 코드가 있다면, 클라이언트용 `import.meta.client`와 서버용 `import.meta.server`를 사용해 분리하는 것을 고려하세요.

:read-more{to="/docs/4.x/directory-structure/app/middleware#when-middleware-runs"}

### Vue 앱 마운트 및 하이드레이트 %{#mount-vue-app-and-hydrate}%

`app.mount('#__nuxt')`를 호출하면 Vue 애플리케이션이 DOM에 마운트됩니다. 애플리케이션이 SSR 또는 SSG 모드를 사용한다면 Vue는 하이드레이션 단계를 수행하여 클라이언트 측 애플리케이션을 상호작용 가능하게 만듭니다. 하이드레이션 중 Vue는 애플리케이션을 다시 만들고([Server Components](/docs/4.x/directory-structure/app/components#server-components) 제외), 각 컴포넌트를 해당 DOM 노드와 일치시킨 뒤 DOM 이벤트 리스너를 연결합니다.

올바른 하이드레이션을 보장하려면 서버와 클라이언트의 데이터 일관성을 유지하는 것이 중요합니다. API 요청의 경우 `useAsyncData`, `useFetch`, 또는 다른 SSR 친화적 컴포저블을 사용하는 것이 권장됩니다. 이러한 방법은 서버 측에서 가져온 데이터가 하이드레이션 중 재사용되도록 보장해 중복 요청을 피하게 해줍니다. 새로운 요청은 하이드레이션이 끝난 후에만 트리거되어야 하며, 이를 통해 하이드레이션 오류를 방지할 수 있습니다.

::callout{icon="i-lucide-lightbulb"}
Vue 애플리케이션을 마운트하기 전에 Nuxt는 [`app:beforeMount`](/docs/4.x/api/advanced/hooks#app-hooks-runtime) 훅을 호출합니다.
::

::callout{icon="i-lucide-lightbulb"}
Vue 애플리케이션을 마운트한 뒤 Nuxt는 [`app:mounted`](/docs/4.x/api/advanced/hooks#app-hooks-runtime) 훅을 호출합니다.
::

### Vue 라이프사이클 %{#vue-lifecycle}%

서버와 달리 브라우저에서는 전체 [Vue 라이프사이클](https://vuejs.org/guide/essentials/lifecycle)이 실행됩니다.
