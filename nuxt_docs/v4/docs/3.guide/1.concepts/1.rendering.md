Nuxt는 [유니버설 렌더링](/docs/4.x/guide/concepts/rendering#universal-rendering), [클라이언트 사이드 렌더링](/docs/4.x/guide/concepts/rendering#client-side-rendering) 같은 다양한 렌더링 모드를 지원하며, [하이브리드 렌더링](/docs/4.x/guide/concepts/rendering#hybrid-rendering)과 [CDN 엣지 서버](/docs/4.x/guide/concepts/rendering#edge-side-rendering)에서 애플리케이션을 렌더링할 가능성도 제공합니다.

브라우저와 서버는 모두 JavaScript 코드를 해석해 Vue.js 컴포넌트를 HTML 요소로 바꿀 수 있습니다. 이 단계를 **렌더링**이라고 합니다. Nuxt는 **유니버설** 렌더링과 **클라이언트 사이드** 렌더링을 모두 지원합니다. 이 두 접근 방식의 장점과 단점은 아래에서 살펴보겠습니다.

기본적으로 Nuxt는 더 나은 사용자 경험과 성능을 제공하고 검색 엔진 인덱싱을 최적화하기 위해 **유니버설 렌더링**을 사용하지만, [한 줄 설정](/docs/4.x/api/nuxt-config#ssr)으로 렌더링 모드를 전환할 수 있습니다.

## 유니버설 렌더링 %{#universal-rendering}%

이 방식은 PHP나 Ruby 애플리케이션이 수행하는 전통적인 **서버 사이드 렌더링**과 유사합니다. 브라우저가 유니버설 렌더링이 활성화된 URL을 요청하면, Nuxt는 서버 환경에서 JavaScript(Vue.js) 코드를 실행하고 완전히 렌더링된 HTML 페이지를 브라우저에 반환합니다. 페이지가 미리 생성되어 있었다면 Nuxt가 캐시에서 완전히 렌더링된 HTML 페이지를 반환할 수도 있습니다. 클라이언트 사이드 렌더링과 달리 사용자는 애플리케이션의 초기 콘텐츠 전체를 즉시 받습니다.

HTML 문서가 다운로드되면 브라우저가 이를 해석하고 Vue.js가 문서를 제어하기 시작합니다. 서버에서 한 번 실행된 같은 JavaScript 코드는 이제 클라이언트(브라우저)에서 백그라운드로 **다시** 실행되며, 리스너를 HTML에 바인딩해 상호작용을 가능하게 합니다(그래서 **유니버설 렌더링**입니다). 이를 **Hydration**이라고 합니다. 하이드레이션이 완료되면 페이지는 동적 인터페이스와 페이지 전환 같은 이점을 누릴 수 있습니다.

유니버설 렌더링을 사용하면 Nuxt 애플리케이션은 빠른 페이지 로드 시간을 제공하면서도 클라이언트 사이드 렌더링의 이점을 유지할 수 있습니다. 또한 콘텐츠가 이미 HTML 문서에 포함되어 있으므로 크롤러가 추가 비용 없이 이를 인덱싱할 수 있습니다.

![HTML 문서가 로드되면 사용자는 정적 콘텐츠에 접근할 수 있습니다. 이후 하이드레이션이 페이지의 상호작용을 가능하게 합니다](/assets/docs/concepts/rendering/ssr.svg)

**무엇이 서버에서 렌더링되고 무엇이 클라이언트에서 렌더링될까요?**

유니버설 렌더링 모드에서 Vue 파일의 어떤 부분이 서버에서, 그리고/또는 클라이언트에서 실행되는지 궁금해하는 것은 자연스러운 일입니다.

```vue [app/app.vue]
<script setup lang="ts">
const counter = ref(0) // 서버와 클라이언트 환경 모두에서 실행됩니다

const handleClick = () => {
  counter.value++ // 클라이언트 환경에서만 실행됩니다
}
</script>

<template>
  <div>
    <p>카운트: {{ counter }}</p>
    <button @click="handleClick">
      증가
    </button>
  </div>
</template>
```

초기 요청 시에는 `counter` ref가 `<p>` 태그 안에서 렌더링되므로 서버에서 초기화됩니다. 여기서 `handleClick`의 내용은 전혀 실행되지 않습니다. 브라우저에서 하이드레이션이 진행되는 동안 `counter` ref는 다시 초기화됩니다. 이후 `handleClick`이 버튼에 바인딩되므로, `handleClick`의 본문은 항상 브라우저 환경에서 실행된다고 보는 것이 타당합니다.

[미들웨어](/docs/4.x/directory-structure/app/middleware)와 [페이지](/docs/4.x/directory-structure/app/pages)는 서버와 하이드레이션 중인 클라이언트에서 실행됩니다. [플러그인](/docs/4.x/directory-structure/app/plugins)은 서버, 클라이언트 또는 양쪽 모두에서 렌더링될 수 있습니다. [컴포넌트](/docs/4.x/directory-structure/app/components)는 클라이언트에서만 실행되도록 강제할 수도 있습니다. [컴포저블](/docs/4.x/directory-structure/app/composables)과 [유틸리티](/docs/4.x/directory-structure/app/utils)는 사용되는 컨텍스트에 따라 렌더링됩니다.

**서버 사이드 렌더링의 장점:**
- **성능**: 브라우저는 JavaScript로 생성된 콘텐츠보다 정적 콘텐츠를 훨씬 빠르게 표시할 수 있으므로, 사용자는 페이지 콘텐츠에 즉시 접근할 수 있습니다. 동시에 Nuxt는 하이드레이션 과정에서 웹 애플리케이션의 상호작용성을 유지합니다.
- **검색 엔진 최적화**: 유니버설 렌더링은 고전적인 서버 애플리케이션처럼 페이지의 전체 HTML 콘텐츠를 브라우저에 전달합니다. 웹 크롤러가 페이지 콘텐츠를 직접 인덱싱할 수 있으므로, 빠르게 인덱싱하고 싶은 모든 콘텐츠에 유니버설 렌더링은 훌륭한 선택입니다.

**서버 사이드 렌더링의 단점:**
- **개발 제약:** 서버와 브라우저 환경은 동일한 API를 제공하지 않기 때문에, 양쪽에서 모두 자연스럽게 실행되는 코드를 작성하는 일은 까다로울 수 있습니다. 다행히 Nuxt는 코드가 어디서 실행되는지 판단할 수 있도록 가이드라인과 특정 변수를 제공합니다.
- **비용:** 페이지를 즉석에서 렌더링하려면 서버가 실행 중이어야 합니다. 이는 기존 서버와 마찬가지로 월간 비용을 추가합니다. 하지만 유니버설 렌더링에서는 클라이언트 측 내비게이션을 브라우저가 이어받기 때문에 서버 호출이 크게 줄어듭니다. [엣지 사이드 렌더링](/docs/4.x/guide/concepts/rendering#edge-side-rendering)을 활용하면 비용을 더 줄일 수 있습니다.

유니버설 렌더링은 매우 범용적이어서 거의 모든 사용 사례에 맞출 수 있으며, 특히 **블로그, 마케팅 웹사이트, 포트폴리오, 전자상거래 사이트, 마켓플레이스** 같은 콘텐츠 중심 웹사이트에 적합합니다.

::tip
하이드레이션 불일치 없이 Vue 코드를 작성하는 더 많은 예제는 [Vue 문서](https://vuejs.org/guide/scaling-up/ssr#hydration-mismatch)를 참고하세요.
::

::important
브라우저 API에 의존하고 부작용이 있는 라이브러리를 임포트할 때는, 해당 라이브러리를 임포트하는 컴포넌트가 클라이언트 측에서만 호출되도록 하세요. 번들러는 부작용이 포함된 모듈의 임포트를 트리 셰이킹하지 않습니다.
::

## 클라이언트 사이드 렌더링 %{#client-side-rendering}%

기본적으로 전통적인 Vue.js 애플리케이션은 브라우저(즉 **클라이언트**)에서 렌더링됩니다. 이후 브라우저가 현재 인터페이스를 만드는 지침이 담긴 모든 JavaScript 코드를 다운로드하고 파싱한 다음, Vue.js가 HTML 요소를 생성합니다.

![사용자는 페이지 콘텐츠를 보기 전에 브라우저가 JavaScript를 다운로드하고 파싱하고 실행할 때까지 기다려야 합니다](/assets/docs/concepts/rendering/csr.svg)

**클라이언트 사이드 렌더링의 장점:**
- **개발 속도**: 전적으로 클라이언트 측에서 작업할 때는 `window` 객체 같은 브라우저 전용 API를 사용하더라도 코드의 서버 호환성을 걱정할 필요가 없습니다.
- **더 저렴함:** 서버를 실행하려면 JavaScript를 지원하는 플랫폼에서 인프라 비용이 추가됩니다. 클라이언트 전용 애플리케이션은 HTML, CSS, JavaScript 파일만으로 어떤 정적 서버에도 호스팅할 수 있습니다.
- **오프라인:** 코드가 완전히 브라우저에서 실행되기 때문에, 인터넷을 사용할 수 없는 동안에도 잘 동작할 수 있습니다.

**클라이언트 사이드 렌더링의 단점:**
- **성능**: 사용자는 브라우저가 JavaScript 파일을 다운로드하고 파싱하고 실행할 때까지 기다려야 합니다. 다운로드는 네트워크 상황에, 파싱과 실행은 사용자의 기기에 따라 좌우되므로 시간이 걸릴 수 있고 사용자 경험에 영향을 줄 수 있습니다.
- **검색 엔진 최적화**: 클라이언트 사이드 렌더링으로 전달된 콘텐츠를 인덱싱하고 업데이트하는 데는 서버 렌더링된 HTML 문서보다 더 많은 시간이 걸립니다. 이는 앞서 설명한 성능 단점과 관련이 있는데, 검색 엔진 크롤러는 첫 시도에서 페이지를 인덱싱하기 위해 인터페이스가 완전히 렌더링될 때까지 기다리지 않기 때문입니다. 순수한 클라이언트 사이드 렌더링에서는 검색 결과 페이지에 콘텐츠가 표시되고 업데이트되기까지 더 오래 걸립니다.

클라이언트 사이드 렌더링은 인덱싱이 필요 없거나 사용자가 자주 방문하는, 상호작용이 많은 **웹 애플리케이션**에 적합한 선택입니다. 브라우저 캐싱을 활용해 이후 방문 시 다운로드 단계를 건너뛸 수 있으므로 **SaaS, 백오피스 애플리케이션, 온라인 게임** 등에 잘 맞습니다.

`nuxt.config.ts`에서 Nuxt의 클라이언트 전용 렌더링을 활성화할 수 있습니다:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  ssr: false,
})
```

::note
`ssr: false`를 사용하는 경우, 앱이 하이드레이션될 때까지 렌더링할 로딩 화면용 HTML을 담은 `~/spa-loading-template.html` 파일도 함께 두어야 합니다.
:read-more{title="SPA Loading Template" to="/docs/4.x/api/configuration/nuxt-config#spaloadingtemplate"}
::

### 정적 클라이언트 렌더링 앱 배포 %{#deploying-a-static-client-rendered-app}%

앱을 `nuxt generate` 또는 `nuxt build --prerender` 명령으로 [정적 호스팅](/docs/4.x/getting-started/deployment#static-hosting)에 배포하면, 기본적으로 Nuxt는 모든 페이지를 각각의 정적 HTML 파일로 렌더링합니다.

::warning
`nuxt generate` 또는 `nuxt build --prerender` 명령으로 앱을 프리렌더링하면 출력 폴더에 서버가 포함되지 않으므로 어떤 서버 엔드포인트도 사용할 수 없습니다. 서버 기능이 필요하다면 대신 `nuxt build`를 사용하세요.
::

순수하게 클라이언트 사이드 렌더링만 사용한다면 이는 불필요할 수 있습니다. 모든 요청에 대해 정적 웹 호스트가 제공하도록 설정할 수 있는 단일 `index.html` 파일과 `200.html`, `404.html` 폴백만 필요할 수도 있습니다.

이를 위해 라우트가 프리렌더링되는 방식을 바꿀 수 있습니다. `nuxt.config.ts`의 [hooks](/docs/4.x/api/advanced/hooks#nuxt-hooks-build-time)에 다음을 추가하세요:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  hooks: {
    'prerender:routes' ({ routes }) {
      routes.clear() // 어떤 라우트도 생성하지 않습니다 (기본값 제외)
    },
  },
})
```

그러면 세 개의 파일이 생성됩니다:

- `index.html`
- `200.html`
- `404.html`

`200.html`과 `404.html`은 사용 중인 호스팅 공급자에 따라 유용할 수 있습니다.

#### 클라이언트 폴백 생성 건너뛰기 %{#skipping-client-fallback-generation}%

클라이언트 렌더링 앱을 프리렌더링할 때 Nuxt는 기본적으로 `index.html`, `200.html`, `404.html` 파일을 생성합니다. 하지만 빌드에서 이 파일들 중 일부 또는 전부가 생성되지 않게 해야 한다면, [Nitro](/docs/4.x/getting-started/prerendering#prerendergenerate-nitro-hook)의 `'prerender:generate'` 훅을 사용할 수 있습니다.

```ts twoslash [nuxt.config.ts]
// @errors: 2353 7006
export default defineNuxtConfig({
  ssr: false,
  nitro: {
    hooks: {
      'prerender:generate' (route) {
        const routesToSkip = ['/index.html', '/200.html', '/404.html']
        if (routesToSkip.includes(route.route)) {
          route.skip = true
        }
      },
    },
  },
})
```

## 하이브리드 렌더링 %{#hybrid-rendering}%

하이브리드 렌더링은 **라우트 규칙**을 사용해 라우트별로 서로 다른 캐싱 규칙을 적용하고, 주어진 URL에 대한 새 요청에 서버가 어떻게 응답할지 결정합니다.

이전에는 Nuxt 애플리케이션과 서버의 모든 라우트/페이지가 유니버설 또는 클라이언트 사이드 중 하나의 동일한 렌더링 모드를 사용해야 했습니다. 하지만 경우에 따라 어떤 페이지는 빌드 시 생성되어야 하고, 다른 페이지는 클라이언트 사이드 렌더링되어야 할 수 있습니다. 예를 들어 관리자 섹션이 있는 콘텐츠 웹사이트를 생각해 보세요. 각 콘텐츠 페이지는 주로 정적이어야 하고 한 번 생성되면 되지만, 관리자 섹션은 인증이 필요하고 더 동적인 애플리케이션처럼 동작합니다.

Nuxt는 라우트 규칙과 하이브리드 렌더링 지원을 포함합니다. 라우트 규칙을 사용하면 Nuxt 라우트 그룹에 대한 규칙을 정의하고, 렌더링 모드를 변경하거나 라우트에 따라 캐시 전략을 지정할 수 있습니다!

Nuxt 서버는 [Nitro 캐싱 레이어](https://nitro.build/guide/cache)를 사용해 해당 미들웨어를 자동으로 등록하고 라우트를 캐시 핸들러로 감쌉니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    // 홈페이지는 빌드 시 프리렌더링됩니다
    '/': { prerender: true },
    // 제품 페이지는 요청 시 생성되고, 백그라운드에서 재검증되며, API 응답이 바뀔 때까지 캐시됩니다
    '/products': { swr: true },
    // 개별 제품 페이지는 요청 시 생성되고, 백그라운드에서 재검증되며, 1시간(3600초) 동안 캐시됩니다
    '/products/**': { swr: 3600 },
    // 블로그 글 목록 페이지는 요청 시 생성되고, 백그라운드에서 재검증되며, CDN에 1시간(3600초) 동안 캐시됩니다
    '/blog': { isr: 3600 },
    // 블로그 글 페이지는 다음 배포까지 한 번만 요청 시 생성되며, CDN에 캐시됩니다
    '/blog/**': { isr: true },
    // 관리자 대시보드는 클라이언트 측에서만 렌더링됩니다
    '/admin/**': { ssr: false },
    // API 라우트에 cors 헤더를 추가합니다
    '/api/**': { cors: true },
    // 레거시 URL을 리디렉션합니다
    '/old-page': { redirect: '/new-page' },
  },
})
```

### 라우트 규칙 %{#route-rules}%

사용할 수 있는 다양한 속성은 다음과 같습니다:
- `redirect: string`{lang=ts} - 서버 측 리디렉션을 정의합니다.
- `ssr: boolean`{lang=ts} - 앱의 일부 구간에 대한 HTML의 서버 사이드 렌더링을 비활성화하고 `ssr: false`로 브라우저에서만 렌더링되도록 합니다
- `cors: boolean`{lang=ts} - `cors: true`로 cors 헤더를 자동으로 추가합니다. `headers`로 덮어써 출력을 사용자 정의할 수 있습니다
- `headers: object`{lang=ts} - 사이트의 특정 구간에 특정 헤더를 추가합니다. 예를 들어 자산에 적용할 수 있습니다
- `swr: number | boolean`{lang=ts} - 서버 응답에 캐시 헤더를 추가하고 설정 가능한 TTL(time to live) 동안 서버 또는 리버스 프록시에 캐시합니다. Nitro의 `node-server` 프리셋은 전체 응답을 캐시할 수 있습니다. TTL이 만료되면 캐시된 응답이 전송되고, 페이지는 백그라운드에서 재생성됩니다. `true`를 사용하면 MaxAge 없이 `stale-while-revalidate` 헤더가 추가됩니다.
- `isr: number | boolean`{lang=ts} - 이 동작은 `swr`와 같지만, 이를 지원하는 플랫폼(현재 Netlify 또는 Vercel)에서는 응답을 CDN 캐시에 추가할 수 있다는 점이 다릅니다. `true`를 사용하면 콘텐츠는 CDN 내부에서 다음 배포까지 유지됩니다.
- `prerender: boolean`{lang=ts} - 빌드 시 라우트를 프리렌더링하고 정적 자산으로 빌드에 포함합니다
- `noScripts: boolean`{lang=ts} - 사이트의 일부 구간에 대해 Nuxt 스크립트와 JS 리소스 힌트의 렌더링을 비활성화합니다.
- `appMiddleware: string | string[] | Record<string, boolean>`{lang=ts} - 애플리케이션의 Vue 앱 부분(즉 Nitro 라우트가 아닌 부분) 안에서 특정 페이지 경로에 대해 실행하거나 실행하지 않아야 하는 미들웨어를 정의할 수 있습니다

::note
`isr` 또는 `swr`를 사용하는 라우트는 HTML과 함께 `_payload.json` 파일도 생성합니다. 클라이언트 측 내비게이션은 데이터를 다시 가져오는 대신 이 캐시된 payload를 로드합니다. `pages/[...slug].vue` 같은 동적 라우트는 `'/**': { isr: true }`처럼 glob 패턴으로 구성하세요.
::

가능한 경우 라우트 규칙은 최적의 성능을 위해 배포 플랫폼의 네이티브 규칙에 자동으로 적용됩니다(현재 Netlify와 Vercel 지원).

::important
[`nuxt generate`](/docs/4.x/api/commands/generate)를 사용할 때는 하이브리드 렌더링을 사용할 수 없다는 점에 유의하세요.
::

## 엣지 사이드 렌더링 %{#edge-side-rendering}%

엣지 사이드 렌더링(ESR)은 Nuxt에 도입된 강력한 기능으로, 콘텐츠 전송 네트워크(CDN)의 엣지 서버를 통해 Nuxt 애플리케이션을 사용자와 더 가까운 곳에서 렌더링할 수 있게 합니다. ESR을 활용하면 성능을 개선하고 지연 시간을 줄여 더 나은 사용자 경험을 제공할 수 있습니다.

ESR에서는 렌더링 과정이 네트워크의 '엣지', 즉 CDN의 엣지 서버로 이동합니다. ESR은 실제 렌더링 모드라기보다 배포 대상에 가깝다는 점에 유의하세요.

페이지 요청이 들어오면 원본 서버까지 가는 대신 가장 가까운 엣지 서버에서 이를 가로챕니다. 이 서버가 페이지용 HTML을 생성해 사용자에게 반환합니다. 이 과정은 데이터가 이동해야 하는 물리적 거리를 최소화하여 **지연 시간을 줄이고 페이지를 더 빠르게 로드**하게 합니다.

엣지 사이드 렌더링은 Nuxt를 구동하는 [서버 엔진](/docs/4.x/guide/concepts/server-engine)인 [Nitro](https://nitro.build/) 덕분에 가능합니다. Nitro는 Node.js, Deno, Cloudflare Workers 등 다양한 플랫폼을 지원합니다.

현재 ESR을 활용할 수 있는 플랫폼은 다음과 같습니다:
- git 통합과 `nuxt build` 명령을 사용해 별도 설정 없이 사용할 수 있는 [Cloudflare Pages](https://pages.cloudflare.com)
- `nuxt build` 명령과 `NITRO_PRESET=vercel-edge` 환경 변수를 사용하는 [Vercel Cloud](https://vercel.com/home)
- `nuxt build` 명령과 `NITRO_PRESET=netlify-edge` 환경 변수를 사용하는 [Netlify Edge Functions](https://www.netlify.com/platform/#netlify-edge-functions)

라우트 규칙과 함께 엣지 사이드 렌더링을 사용할 때는 **하이브리드 렌더링**도 함께 사용할 수 있습니다.
