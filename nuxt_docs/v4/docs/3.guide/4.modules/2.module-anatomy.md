Nuxt 모듈에는 두 가지 유형이 있습니다:

- published modules는 npm에 배포됩니다. 일부 커뮤니티 모듈 목록은 [Nuxt 웹사이트](/modules)에서 확인할 수 있습니다.
- "local" modules는 Nuxt 프로젝트 내부에 존재하며, [Nuxt config에 인라인으로 작성](/docs/4.x/api/nuxt-config#modules)되거나 [`modules` 디렉터리](/docs/4.x/directory-structure/modules) 안에 위치합니다.

어느 경우든 동일한 방식으로 동작합니다.

## 모듈 정의하기 %{#define-your-module}%

::note
스타터를 사용하는 경우 모듈 정의는 `src/module.ts`에 있습니다.
::

모듈 정의는 모듈의 진입점입니다. Nuxt 구성을 통해 모듈이 참조될 때 Nuxt가 로드하는 대상입니다.

저수준에서 Nuxt 모듈 정의는 인라인 사용자 옵션과 Nuxt와 상호작용하기 위한 `nuxt` 객체를 받는 단순한, 필요에 따라 비동기식일 수 있는 함수입니다.

```ts
export default function (inlineOptions, nuxt) {
  // 여기서 원하는 작업을 수행할 수 있습니다.
  console.log(inlineOptions.token) // `123`
  console.log(nuxt.options.dev) // `true` or `false`
  nuxt.hook('ready', (nuxt) => {
    console.log('Nuxt 준비 완료')
  })
}
```

[Nuxt Kit](/docs/4.x/guide/going-further/kit)가 제공하는 상위 수준 `defineNuxtModule` 헬퍼를 사용하면 이 함수에 대한 타입 힌트를 얻을 수 있습니다.

```ts
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule((options, nuxt) => {
  nuxt.hook('pages:extend', (pages) => {
    console.log(`Discovered ${pages.length} pages`)
  })
})
```

하지만 이런 저수준 함수 정의를 사용하는 것은 **권장하지 않습니다**. 대신 모듈을 정의할 때는, 특히 npm에 배포할 경우 모듈을 식별하는 `meta` 속성이 있는 객체 문법 사용을 **권장합니다**.

이 헬퍼는 모듈에 필요한 여러 공통 패턴을 구현해 Nuxt 모듈 작성을 더 단순하게 만들고, 향후 호환성을 보장하며, 모듈 작성자와 사용자 모두의 경험을 개선합니다.

```ts
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: {
    // 보통 모듈의 npm 패키지 이름입니다
    name: '@nuxtjs/example',
    // `nuxt.config`에서 모듈 옵션을 담는 키입니다
    configKey: 'sample',
    // 호환성 제약 조건
    compatibility: {
      // 지원되는 nuxt 버전의 semver 버전
      nuxt: '>=3.0.0',
    },
  },
  // 모듈의 기본 설정 옵션이며, 이를 반환하는 함수일 수도 있습니다
  defaults: {},
  // Nuxt 훅을 등록하는 축약 문법
  hooks: {},
  // 다른 모듈을 위한 구성입니다. 이것이 해당 모듈이
  // 여러분의 모듈보다 먼저 실행된다는 것을 보장하지는 않지만, 실행되기 전에 다른 모듈의 구성을 변경할 수 있게 합니다
  moduleDependencies: {
    'some-module': {
      // 모듈의 버전 제약을 지정할 수 있습니다. 사용자가 다른
      // 버전을 설치한 경우 Nuxt는 시작 시 오류를 발생시킵니다.
      version: '>=2',
      // 기본적으로 moduleDependencies는 `optional`이 설정되지 않는 한
      // Nuxt가 설치할 모듈 목록에 추가됩니다.
      optional: true,
      // `nuxt.options`를 덮어써야 하는 모든 구성입니다.
      overrides: {},
      // 설정되어야 하는 모든 구성입니다. 모듈 기본값은 덮어쓰지만
      // `nuxt.options`에 설정된 구성은 덮어쓰지 않습니다.
      defaults: {},
    },
  },
  // 모듈 로직을 담는 함수이며 비동기식일 수 있습니다
  setup (moduleOptions, nuxt) {
    // ...
  },
})
```

`defineNuxtModule`은 더 저수준인 `(inlineOptions, nuxt)` 모듈 시그니처를 가진 래퍼 함수를 반환합니다. 이 래퍼 함수는 `setup` 함수를 호출하기 전에 기본값과 기타 필요한 단계를 적용합니다:

- 모듈 옵션 자동 병합을 위한 `defaults` 및 `meta.configKey` 지원
- 타입 힌트와 자동 타입 추론
- `meta.name` 또는 `meta.configKey`에서 계산된 고유 키를 사용해 모듈이 한 번만 설치되도록 보장
- Nuxt 훅 자동 등록
- 모듈 메타를 기반으로 한 호환성 문제 자동 검사
- Nuxt 내부 사용을 위한 `getOptions` 및 `getMeta` 노출
- 모듈이 최신 버전의 `@nuxt/kit`에서 가져온 `defineNuxtModule`을 사용하는 한 하위 및 상위 호환성 보장
- 모듈 빌더 도구와의 통합

## 런타임 코드 추가 %{#add-runtime-code}%

::note
스타터를 사용하는 경우 runtime 디렉터리는 `src/runtime/`입니다.
::

모듈은 Nuxt 구성의 다른 모든 항목과 마찬가지로 애플리케이션 런타임에 포함되지 않습니다. 하지만 모듈이 설치된 애플리케이션에 런타임 코드를 제공하거나 주입하고 싶을 수 있습니다. runtime 디렉터리는 바로 이 작업을 가능하게 합니다.

runtime 디렉터리 안에서는 Nuxt 앱과 관련된 모든 종류의 자산을 제공할 수 있습니다:
- Vue components
- Composables
- [Nuxt plugins](/docs/4.x/directory-structure/app/plugins)

[server engine](/docs/4.x/guide/concepts/server-engine)인 Nitro에는 다음을 제공할 수 있습니다:
- API routes
- Middlewares
- Nitro plugins

또는 사용자의 Nuxt 애플리케이션에 주입하고 싶은 다른 모든 종류의 자산도 가능합니다:
- Stylesheets
- 3D models
- Images
- etc.

그런 다음 [모듈 정의](#define-your-module)에서 이 모든 자산을 애플리케이션 안으로 주입할 수 있습니다.

::tip
[the recipes section](/docs/4.x/guide/modules/recipes-basics)에서 자산 주입에 대해 더 알아보세요.
::

::warning
배포된 모듈은 runtime 디렉터리 내부 자산에 대해 auto-import를 활용할 수 없습니다. 대신 `#imports` 또는 이와 유사한 곳에서 명시적으로 import해야 합니다.
:br :br
성능상의 이유로 `node_modules` 내부 파일(배포된 모듈이 최종적으로 위치하게 될 곳)에는 auto-import가 활성화되지 않습니다.
::
