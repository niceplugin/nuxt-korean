강력한 기능에는 그만큼 큰 책임이 따릅니다. 모듈은 강력하지만, 애플리케이션의 성능과 뛰어난 개발자 경험을 유지하기 위해 모듈을 작성할 때 염두에 둘 몇 가지 모범 사례가 있습니다.

## 비동기 설정 처리하기 %{#handle-async-setup}%

앞서 보았듯이 Nuxt 모듈은 비동기식일 수 있습니다. 예를 들어, 일부 API를 가져오거나 비동기 함수를 호출해야 하는 모듈을 개발하고 싶을 수 있습니다.

하지만 비동기 동작은 주의해야 합니다. Nuxt는 다음 모듈로 넘어가고 개발 서버, 빌드 프로세스 등을 시작하기 전에 모듈 설정이 끝나기를 기다리기 때문입니다. 시간이 오래 걸리는 로직은 Nuxt 훅으로 미루는 편이 좋습니다.

::warning
모듈 설정에 **1초** 이상 걸리면 Nuxt가 이에 대한 경고를 출력합니다.
::

## 노출 항목에 접두사 붙이기 %{#prefix-your-exports}%

Nuxt 모듈은 다른 모듈, Nuxt 내부 구현, 또는 사용자 정의 코드와의 충돌을 피하기 위해 노출하는 모든 설정, 플러그인, API, 컴포저블, 컴포넌트, 서버 라우트에 명시적인 접두사를 제공해야 합니다.

이상적으로는 모듈 이름을 접두사로 붙이세요. 예를 들어 모듈 이름이 `nuxt-foo`라면:

| 유형 | ❌ 피하기 | ✅ 권장 |
| --- | --- | --- |
| Components | `<Button>`, `<Modal>` | `<FooButton>`, `<FooModal>` |
| Composables | `useData()`, `useModal()` | `useFooData()`, `useFooModal()` |
| Server routes | `/api/track`, `/api/data` | `/api/_foo/track`, `/api/_foo/data` |

### 서버 라우트 %{#server-routes}%

이 점은 특히 서버 라우트에서 중요합니다. `/api/auth`, `/api/login`, `/api/user` 같은 일반적인 경로는 애플리케이션에서 이미 사용 중일 가능성이 매우 높기 때문입니다.

모듈 이름을 기반으로 한 고유한 접두사를 사용하세요:
- `/api/_foo/...` (밑줄 접두사 사용)
- `/_foo/...` (비 API 라우트용)

## 라이프사이클 훅 사용하기 %{#use-lifecycle-hooks}%

모듈에서 일회성 설정 작업(구성 파일 생성, 데이터베이스 설정, 의존성 설치 등)을 수행해야 한다면, 메인 `setup` 함수에서 해당 로직을 실행하는 대신 라이프사이클 훅을 사용하세요.

```ts
import { addServerHandler, defineNuxtModule } from 'nuxt/kit'
import semver from 'semver'

export default defineNuxtModule({
  meta: {
    name: 'my-database-module',
    version: '1.0.0',
  },
  async onInstall (nuxt) {
    // 일회성 설정: 데이터베이스 스키마 생성, 구성 파일 생성 등
    await generateDatabaseConfig(nuxt.options.rootDir)
  },
  async onUpgrade (nuxt, options, previousVersion) {
    // 버전별 마이그레이션 처리
    if (semver.lt(previousVersion, '1.0.0')) {
      await migrateLegacyData()
    }
  },
  setup (options, nuxt) {
    // 모든 빌드에서 실행되는 일반 설정 로직
    addServerHandler({ /* ... */ })
  },
})
```

이 패턴은 모든 빌드에서 불필요한 작업이 수행되는 것을 막고 더 나은 개발자 경험을 제공합니다. 자세한 내용은 [라이프사이클 훅 문서](/docs/4.x/api/kit/modules#using-lifecycle-hooks-for-module-installation-and-upgrade)를 참고하세요.

## TypeScript 친화적으로 만들기 %{#be-typescript-friendly}%

Nuxt는 최상의 개발자 경험을 위해 일급 TypeScript 통합을 제공합니다.

타입을 노출하고 TypeScript로 모듈을 개발하면, 사용자가 TypeScript를 직접 사용하지 않더라도 이점을 얻을 수 있습니다.

## ESM 구문 사용하기 %{#use-esm-syntax}%

Nuxt는 네이티브 ESM에 의존합니다. 자세한 내용은 [네이티브 ES 모듈](/docs/4.x/guide/concepts/esm)을 참고하세요.

## 모듈 문서화하기 %{#document-your-module}%

README 파일에 모듈 사용법을 문서화하는 것을 고려해 보세요:

- 왜 이 모듈을 사용해야 하나요?
- 이 모듈은 어떻게 사용하나요?
- 이 모듈은 무엇을 하나요?

통합 웹사이트와 문서로 연결하는 링크를 제공하는 것은 언제나 좋은 생각입니다.

## 데모 제공하기 %{#provide-a-demo}%

모듈과 [StackBlitz](https://nuxt.new/s/v4)를 이용한 최소 재현 예제를 만들어 모듈 README에 추가하는 것은 좋은 실천 방법입니다.

이렇게 하면 잠재적인 사용자에게 모듈을 빠르고 쉽게 실험할 방법을 제공할 뿐 아니라, 문제가 발생했을 때 당신에게 보낼 최소 재현 예제를 손쉽게 만들 수 있는 방법도 함께 제공할 수 있습니다.

## 특정 버전에 종속되지 않기 %{#stay-version-agnostic}%

Nuxt, Nuxt Kit, 그리고 기타 새로운 도구들은 전방 및 후방 호환성을 모두 염두에 두고 만들어졌습니다.

생태계의 파편화를 피하기 위해 "X for Nuxt 3" 대신 "X for Nuxt"를 사용하고, Nuxt 버전 제약을 설정할 때는 `meta.compatibility`를 사용하는 편이 좋습니다.

## 스타터 규칙 따르기 %{#follow-starter-conventions}%

모듈 스타터에는 기본 도구 및 구성 세트(예: ESLint 구성)가 포함되어 있습니다. 모듈을 오픈 소스로 공개할 계획이라면 이러한 기본값을 유지하는 것이 다른 [커뮤니티 모듈](/modules)과 일관된 코딩 스타일을 공유하게 해 주므로, 다른 사람들이 기여하기 더 쉬워집니다.
