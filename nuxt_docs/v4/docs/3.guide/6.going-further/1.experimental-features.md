Nuxt에는 구성 파일에서 활성화할 수 있는 실험적 기능이 포함되어 있습니다.

내부적으로 Nuxt는 이러한 실험적 기능을 정의하기 위해 `@nuxt/schema`를 사용합니다. 더 자세한 정보는 [API 문서](/docs/4.x/guide/going-further/experimental-features)나 [소스 코드](https://github.com/nuxt/nuxt/blob/main/packages/schema/src/config/experimental.ts)를 참고할 수 있습니다.

::note
이 기능들은 실험적이며 향후 제거되거나 수정될 수 있다는 점에 유의하세요.
::

## alwaysRunFetchOnKeyChange %{#alwaysrunfetchonkeychange}%

`immediate: false`로 설정되어 있고 아직 트리거되지 않았더라도, 키가 변경될 때 `useFetch`를 실행할지 여부입니다.

`useFetch`와 `useAsyncData`는 `immediate: true`이거나 이미 한 번 트리거된 경우 키가 바뀌면 항상 실행됩니다.

이 플래그는 기본적으로 비활성화되어 있지만, 다음과 같이 활성화할 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    alwaysRunFetchOnKeyChange: true,
  },
})
```

이 플래그는 기본적으로 활성화되어 있지만, 다음과 같이 비활성화할 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    appManifest: false,
  },
})
```

## asyncContext %{#asynccontext}%

Nuxt와 Nitro에서 중첩된 composable이 네이티브 async context에 접근할 수 있도록 활성화합니다. 이를 통해 async composable 내부에서 composable을 사용할 수 있고 `Nuxt instance is unavailable` 오류가 발생할 가능성을 줄일 수 있습니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    asyncContext: true,
  },
})
```

## extractAsyncDataHandlers %{#extractasyncdatahandlers}%

더 나은 코드 분할과 캐시 효율을 위해 `useAsyncData`와 `useLazyAsyncData` 호출에서 handler 함수를 별도 청크로 추출합니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    extractAsyncDataHandlers: true,
  },
})
```

이 기능은 인라인 handler 함수를 동적으로 import되는 청크로 변환합니다:

```vue
<!-- 이전 -->
<script setup>
const { data } = await useAsyncData('user', async () => {
  return await $fetch('/api/user')
})
</script>
```

```vue
<!-- 변환 후 -->
<script setup>
const { data } = await useAsyncData('user', () =>
  import('/generated-chunk.js').then(r => r.default()),
)
</script>
```

이 변환의 장점은 필요 시 코드를 로드할 수 있게 유지하면서도 데이터 가져오기 로직을 분리할 수 있다는 점입니다.

::important
이 기능은 payload 추출이 활성화된 **정적 빌드**에서만, 그리고 런타임에 데이터를 다시 가져올 필요가 없는 경우에만 권장됩니다.
::

## emitRouteChunkError %{#emitroutechunkerror}%

vite/webpack 청크를 로드하는 중 오류가 발생했을 때 `app:chunkError` 훅을 발생시킵니다. 기본 동작은 새 라우트로 이동할 때 청크 로드에 실패하면 해당 새 라우트를 다시 로드하는 것입니다.

기본적으로 Nuxt는 새 라우트로 이동하는 동안 청크 로드에 실패하면 새 라우트를 다시 로드합니다 (`automatic`).

`automatic-immediate`로 설정하면 청크 로드에 실패하는 즉시 Nuxt가 현재 라우트를 다시 로드합니다(내비게이션을 기다리지 않음). 이는 Nuxt 앱이 [lazy component](/docs/4.x/directory-structure/app/components#dynamic-imports)를 로드하지 못하는 경우처럼, 내비게이션으로 트리거되지 않는 청크 오류에 유용합니다. 다만 앱에 오류를 일으킨 청크가 실제로 필요하지 않은 경우 등, 원치 않는 다시 로드가 발생할 수 있다는 단점이 있습니다.

이 값을 `false`로 설정하면 자동 처리를 비활성화할 수 있고, `manual`로 설정하면 청크 오류를 직접 처리할 수 있습니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    emitRouteChunkError: 'automatic', // 또는 'automatic-immediate', 'manual', false
  },
})
```

## restoreState %{#restorestate}%

청크 오류 또는 수동 [`reloadNuxtApp()`](/docs/4.x/api/utils/reload-nuxt-app) 호출 이후 페이지를 다시 로드할 때 `sessionStorage`에서 Nuxt 앱 상태를 복원할 수 있게 합니다.

hydration 오류를 피하기 위해 Vue 앱이 마운트된 이후에만 적용되므로, 초기 로드 시 화면이 잠깐 깜박일 수 있습니다.

::important
이 기능은 예상치 못한 동작을 일으킬 수 있으므로 활성화 전에 신중히 검토하세요.
그리고 자동 생성 키가 빌드 간에 일치하지 않을 수 있으므로 [`useState`](/docs/4.x/api/composables/use-state)에 명시적 키를 제공하는 것을 고려하세요.
::

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    restoreState: true,
  },
})
```

## payloadExtraction %{#payloadextraction}%

사전 렌더링되거나 캐시된(ISR/SWR) 페이지에 대해 payload 데이터가 전달되는 방식을 제어합니다.

- `'client'` - 초기 서버 렌더에서는 payload가 HTML에 인라인으로 포함되고, 클라이언트 사이드 내비게이션을 위해 `_payload.json` 파일로 추출됩니다. 이렇게 하면 초기 로드 시 별도의 네트워크 요청을 피하면서도 효율적인 클라이언트 사이드 내비게이션을 유지할 수 있습니다.
- `true` - 초기 서버 렌더와 클라이언트 사이드 내비게이션 모두에서 payload가 별도의 `_payload.json` 파일로 추출됩니다.
- `false` - payload 추출이 완전히 비활성화됩니다. payload는 항상 HTML에 인라인으로 포함되며 `_payload.json` 파일은 생성되지 않습니다.

기본값은 `true`이며, `compatibilityVersion: 5`가 설정되면 `'client'`가 기본값입니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    // HTML에는 payload를 인라인으로 넣고, 클라이언트 사이드 내비게이션에만 추출
    payloadExtraction: 'client',
  },
})
```

payload 추출은 ISR(Incremental Static Regeneration) 또는 SWR(Stale-While-Revalidate) 캐싱 전략을 사용하는 라우트에서도 동작합니다. 이를 통해 CDN이 HTML과 함께 payload 파일도 캐시할 수 있어, 캐시된 라우트에서 클라이언트 사이드 내비게이션 성능을 향상시킬 수 있습니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    payloadExtraction: 'client',
  },
  routeRules: {
    // 이 캐시된 라우트들에 대해 payload 파일이 생성됩니다
    '/products/**': { isr: 3600 },
    '/blog/**': { swr: true },
  },
})
```

## clientNodePlaceholder %{#clientnodeplaceholder}%

서버 사이드 렌더링 중 client-only 컴포넌트의 placeholder로 `<div>` 요소 대신 comment node(`<!--placeholder-->`)를 사용합니다.

활성화하면 `.client.vue` 컴포넌트와 `createClientOnly()` 래퍼는 서버에서 빈 `<div>` 대신 HTML 주석을 렌더링합니다. 이렇게 하면 placeholder `<div>`와 실제 컴포넌트 루트가 같은 태그 이름을 공유할 때 scoped style이 적용되지 않을 수 있는 Vue hydration 문제를 해결할 수 있습니다.

::warning
이 기능을 활성화하면 `.client.vue` 컴포넌트에 전달한 속성(`class`, `style` 등)이 SSR HTML에 나타나지 않습니다. 레이아웃 이동을 방지하기 위해 스타일이 적용된 placeholder가 필요하다면 대신 `#fallback` 슬롯과 함께 `<ClientOnly>`를 사용하세요.
::

이 플래그는 `future.compatibilityVersion`이 `5` 이상으로 설정되면 활성화되지만, 다음과 같이 명시적으로 활성화할 수도 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    clientNodePlaceholder: true,
  },
})
```

## watcher %{#watcher}%

Nuxt의 watching 서비스로 사용할 대체 watcher를 설정합니다.

Nuxt는 기본적으로 `chokidar-granular`를 사용하며, 이 watcher는 최상위 디렉터리
(`node_modules`, `.git` 등) 중 감시 대상에서 제외된 것들을 무시합니다.

이를 `parcel`로 설정해 `@parcel/watcher`를 사용할 수도 있으며, 이는
대규모 프로젝트나 Windows 플랫폼에서 성능을 개선할 수 있습니다.

또는 `chokidar`로 설정해 소스 디렉터리의 모든 파일을 감시할 수도 있습니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    watcher: 'chokidar-granular', // 'chokidar' 또는 'parcel'도 선택할 수 있습니다
  },
})
```

## sharedPrerenderData %{#sharedprerenderdata}%

Nuxt는 사전 렌더링되는 페이지 사이에서 payload *data*를 자동으로 공유합니다. 이는 `useAsyncData` 또는 `useFetch`를 사용해 서로 다른 페이지에서 동일한 데이터를 가져오는 사이트를 prerender할 때 상당한 성능 향상을 가져올 수 있습니다.

필요하다면 이 기능을 비활성화할 수 있습니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    sharedPrerenderData: false,
  },
})
```

:video-accordion{title="Alexander Lichter가 실험적 sharedPrerenderData를 설명하는 영상을 시청하세요" videoId="1jUupYHVvrU"}

이 기능을 활성화할 때는 특히 데이터의 고유 키가 어떤 경우에도 같은 데이터로
항상 해석되도록 보장하는 것이 중요합니다. 예를 들어 `useAsyncData`를 사용해
특정 페이지와 관련된 데이터를 가져온다면, 그 데이터에 고유하게 대응하는 키를 제공해야 합니다. (`useFetch`
는 자동으로 이를 처리해 주어야 합니다.)

```ts
// 동적 페이지(예: `[slug].vue`)에서는 route slug가 가져오는 데이터에 영향을 주므로 안전하지 않습니다
// 하지만 키에는 그것이 반영되지 않아 Nuxt는 이를 알 수 없습니다.
const route = useRoute()
const { data } = await useAsyncData(async (_nuxtApp, { signal }) => {
  return await $fetch(`/api/my-page/${route.params.slug}`, { signal })
})
// 대신 가져온 데이터를 고유하게 식별하는 키를 사용해야 합니다.
const { data } = await useAsyncData(route.params.slug, async (_nuxtApp, { signal }) => {
  return await $fetch(`/api/my-page/${route.params.slug}`, { signal })
})
```

## normalizeComponentNames %{#normalizecomponentnames}%

Nuxt는 자동 생성되는 Vue 컴포넌트 이름을, 컴포넌트를 auto-import할 때 사용하는 전체 컴포넌트 이름과 일치하도록 갱신합니다.

문제가 발생한다면 이 기능을 비활성화할 수 있습니다.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizeComponentNames: false,
  },
})
```

기본적으로, 직접 설정하지 않았다면 Vue는 다음과 같이 컴포넌트 이름을 부여합니다
컴포넌트 파일명과 일치하는 이름을 사용합니다.

```bash [Directory structure]
├─ components/
├─── SomeFolder/
├───── MyComponent.vue
```

이 경우 Vue 관점에서 컴포넌트 이름은 `MyComponent`가 됩니다. `<KeepAlive>`와 함께 사용하거나 Vue DevTools에서 식별하려면 이 컴포넌트 이름을 사용해야 합니다.

하지만 auto-import하려면 `SomeFolderMyComponent`를 사용해야 합니다.

`experimental.normalizeComponentNames`를 설정하면 이 두 값이 일치하게 되며, Vue는 Nuxt의 컴포넌트 이름 규칙과 일치하는 컴포넌트 이름을 생성합니다.

## normalizePageNames %{#normalizepagenames}%

페이지 컴포넌트 이름이 해당 라우트 이름과 일치하도록 보장합니다. 이를 통해 페이지 컴포넌트의 `__name` 속성이 설정되어 Vue의 `<KeepAlive>`가 이름으로 이를 올바르게 식별할 수 있습니다.

기본적으로 Vue는 파일명을 기준으로 컴포넌트 이름을 부여합니다. 예를 들어 `pages/foo/index.vue`와 `pages/bar/index.vue`는 둘 다 `index`라는 컴포넌트 이름을 갖게 됩니다. 이렇게 되면 여러 페이지가 같은 이름을 공유하므로 이름 기반 `<KeepAlive>` 필터링이 신뢰할 수 없게 됩니다.

`normalizePageNames`를 활성화하면 페이지 컴포넌트는 라우트 이름(예: `foo`, `bar`)을 따라 이름이 지정되므로, 각 페이지에 `defineOptions({ name: '...' })`를 수동으로 추가하지 않고도 `<KeepAlive>`의 `include`/`exclude`를 사용할 수 있습니다.

이 플래그는 `future.compatibilityVersion`이 `5` 이상으로 설정되면 활성화되지만, 다음과 같이 비활성화할 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizePageNames: false,
  },
})
```

```vue [app.vue]
<template>
  <NuxtPage :keepalive="{ include: ['foo'] }" />
</template>
```

## decorators %{#decorators}%

이 옵션은 Nuxt/Nitro 앱 전체에서 decorator 문법을 활성화합니다.

Vite builder(기본값)를 사용할 때 decorator는 [`@babel/plugin-proposal-decorators`](https://babeljs.io/docs/babel-plugin-proposal-decorators)를 사용하는 [Babel](https://babeljs.io/)을 통해 하향 변환됩니다. webpack 또는 rspack builder를 사용할 때 decorator는 [esbuild](https://github.com/evanw/esbuild/releases/tag/v0.21.3)를 통해 하향 변환됩니다.

오랫동안 TypeScript는 `compilerOptions.experimentalDecorators`를 통해 decorator를 지원해 왔습니다. 이 구현은 TC39 표준화 과정 이전의 것이었습니다. 이제 decorator는 [Stage 3 Proposal](https://github.com/tc39/proposal-decorators)이며 TS 5.0+에서 별도 구성 없이 지원됩니다 (https://github.com/microsoft/TypeScript/pull/52582 및 https://devblogs.microsoft.com/typescript/announcing-typescript-5-0-beta/#decorators 참고).

`experimental.decorators`를 활성화하면 TypeScript의 이전 `compilerOptions.experimentalDecorators` 구현이 아니라, TC39 제안에 대한 지원이 활성화됩니다.

::warning
이 기능은 최종적으로 JS 표준에 포함되기 전까지 변경될 수 있다는 점에 유의하세요.
::

### 사용법 %{#usage}%

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    decorators: true,
  },
})
```

Vite builder 또는 Nitro 서버 빌드를 사용할 때는 추가 Babel 패키지를 dev dependency로 설치해야 합니다:

::code-group
```bash [npm]
npm install -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
```bash [pnpm]
pnpm add -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
```bash [yarn]
yarn add -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
::

::tip
아직 설치되어 있지 않다면 Nuxt가 자동으로 설치를 안내합니다.
::

```ts [app/app.vue]
function something (_method: () => unknown) {
  return () => 'decorated'
}

class SomeClass {
  @something
  public someMethod () {
    return 'initial'
  }
}

const value = new SomeClass().someMethod()
// 이것은 'decorated'를 반환합니다
```

## granularCachedData %{#granularcacheddata}%

`useAsyncData`와 `useFetch`에서 데이터를 새로 고칠 때(`watch`, `refreshNuxtData()`, 수동 `refresh()` 호출을 통해) `getCachedData`의 결과를 호출하고 사용할지 여부입니다.

이 플래그는 기본적으로 활성화되어 있지만, 다음과 같이 비활성화할 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    granularCachedData: false,
  },
})
```

::read-more{icon="i-simple-icons-github" color="gray" to="https://github.com/nuxt/nuxt/pull/31373" target="_blank"}
구현 세부 사항은 PR #31373를 참고하세요.
::

## headNext %{#headnext}%

head 최적화를 사용합니다:

- head 안의 태그를 더 성능 좋게 렌더링하기 위해 capo.js head plugin을 추가합니다.
- 초기 hydration을 줄이기 위해 hash hydration plugin을 사용합니다

이 플래그는 기본적으로 활성화되어 있지만, 다음과 같이 비활성화할 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    headNext: false,
  },
})
```

## pendingWhenIdle %{#pendingwhenidle}%

`useAsyncData`와 `useFetch`에서 데이터 가져오기가 아직 시작되지 않았을 때 `pending`을 `true`로 둘지 여부입니다.

이 플래그는 기본적으로 비활성화되어 있지만, 다음과 같이 활성화할 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    pendingWhenIdle: true,
  },
})
```

## entryImportMap %{#entryimportmap}%

기본적으로 Nuxt는 import map을 사용해 번들의 entry chunk를 해석함으로써 청크 안정성을 높입니다.

이 기능은 `<head>` 태그의 맨 위에 import map을 주입합니다:

```html
<script type="importmap">{"imports":{"#entry":"/_nuxt/DC5HVSK5.js"}}</script>
```

Vite가 생성한 스크립트 청크 내부에서는 `#entry`에서 import합니다. 즉 entry가 변경되어도, 그 외 변경이 없는 청크는 무효화되지 않습니다.

::note
Nuxt는 import map을 지원하지 않는 브라우저가 `vite.build.target`에 포함되어 있거나, `vite.build.rolldownOptions.output.entryFileNames`가 `[hash]`를 포함하지 않는 값으로 설정되어 있는 경우 이 기능을 똑똑하게 비활성화합니다.
::

이 기능을 비활성화해야 한다면 다음과 같이 할 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    entryImportMap: false,
  },
  // 또는 더 나은 방법으로, 원하는 target을 vite에 알려주면
  // nuxt가 이를 존중합니다
  vite: {
    build: {
      target: 'safari13',
    },
  },
})
```

## typescriptPlugin %{#typescriptplugin}%

`@dxup/nuxt` 모듈을 통해 향상된 TypeScript 개발자 경험을 활성화합니다.

이 실험적 플러그인은 Nuxt 애플리케이션에서 TypeScript를 사용할 때 더 나은 DX를 위해 TypeScript 통합과 개발 도구를 개선합니다.

이 플래그는 기본적으로 비활성화되어 있지만, 다음과 같이 활성화할 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    typescriptPlugin: true,
  },
})
```

::important
이 기능을 사용하려면 다음이 필요합니다:
- `typescript`가 의존성으로 설치되어 있어야 합니다
- VS Code가 워크스페이스 TypeScript 버전을 사용하도록 설정해야 합니다 ([VS Code documentation](https://code.visualstudio.com/docs/typescript/typescript-compiling#_using-the-workspace-version-of-typescript) 참고)
::
