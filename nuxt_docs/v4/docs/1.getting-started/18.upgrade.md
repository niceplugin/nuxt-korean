## Nuxt 업그레이드 %{#upgrading-nuxt}%

### 최신 릴리스 %{#latest-release}%

Nuxt를 [최신 릴리스](https://github.com/nuxt/nuxt/releases)로 업그레이드하려면 `nuxt upgrade` 명령을 사용하세요.

::code-group{sync="pm"}

```bash [npm]
npx nuxt upgrade
```

```bash [yarn]
yarn nuxt upgrade
```

```bash [pnpm]
pnpm nuxt upgrade
```

```bash [bun]
bun x nuxt upgrade
```

```bash [deno]
deno x nuxt upgrade
```

::

### 나이틀리 릴리스 채널 %{#nightly-release-channel}%

최신 Nuxt 빌드와 테스트 기능을 정식 릴리스 전에 사용하려면 [나이틀리 릴리스 채널](/docs/4.x/guide/going-further/nightly-release-channel) 가이드를 읽어보세요.

## Nuxt 5 테스트하기 %{#testing-nuxt-5}%

Nuxt 5는 **현재 개발 중**입니다. 정식 릴리스 전까지는 Nuxt 4.2+ 버전에서 Nuxt 5의 여러 브레이킹 체인지를 시험해볼 수 있습니다.

### Nuxt 5 동작 미리 사용하기 %{#opting-in-to-nuxt-5}%

먼저 Nuxt를 [최신 릴리스](https://github.com/nuxt/nuxt/releases)로 업그레이드하세요.

그다음 `future.compatibilityVersion`을 설정해 Nuxt 5 동작에 맞출 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  future: {
    compatibilityVersion: 5,
  },
})
```

`future.compatibilityVersion`을 `5`로 설정하면 Nuxt 설정 전반의 기본값이 Nuxt v5 동작에 맞게 바뀝니다. 여기에는 다음이 포함됩니다:

- **Vite Environment API**: 더 나은 빌드 설정을 위해 새로운 [Vite Environment API](/docs/4.x/getting-started/upgrade#migration-to-vite-environment-api)를 사용합니다
- **정규화된 페이지 이름**: 일관된 `<KeepAlive>` 동작을 위해 페이지 컴포넌트 이름이 [라우트 이름과 일치](/docs/4.x/getting-started/upgrade#normalized-page-component-names)하게 됩니다
- **`clearNuxtState`가 기본값으로 재설정됨**: `clearNuxtState`는 상태를 `undefined`로 설정하는 대신 [초기값으로 재설정](/docs/4.x/getting-started/upgrade#respect-defaults-when-clearing-usestate)합니다
- **비동기 아님 `callHook`**: [`callHook`가 항상 `Promise`를 반환하는 대신 `void`를 반환할 수 있습니다](/docs/4.x/getting-started/upgrade#non-async-callhook)
- **주석 노드 플레이스홀더**: 클라이언트 전용 컴포넌트가 SSR 플레이스홀더로 [`<div>` 대신 주석 노드](/docs/4.x/getting-started/upgrade#client-only-comment-placeholders)를 사용하여 scoped styles hydration 문제를 해결합니다
- 그 밖에 제공되는 Nuxt 5 개선 사항과 변경점

::note
이 섹션은 정식 릴리스 전까지 변경될 수 있으므로 `future.compatibilityVersion: 5`로 Nuxt 5를 테스트 중이라면 정기적으로 다시 확인하세요.
::

브레이킹 체인지나 중요한 변경 사항은 이전/이후 버전 호환을 위한 마이그레이션 단계와 함께 아래에 정리됩니다.

### Vite Environment API로 마이그레이션 %{#migration-to-vite-environment-api}%

🚦 **영향도**: 중간

#### 무엇이 바뀌었나 %{#what-changed}%

Nuxt 5는 환경 개념을 공식화하고 환경별 설정 제어를 더 잘할 수 있게 해주는 Vite 6의 새로운 [Environment API](https://vite.dev/guide/api-environment)로 마이그레이션합니다.

이전에는 Nuxt가 클라이언트와 서버용 Vite 설정을 별도로 사용했습니다. 이제는 특정 환경을 대상으로 하기 위해 `applyToEnvironment()` 메서드를 사용하는 환경별 플러그인과 함께 공유 Vite 설정을 사용합니다.

::note
Vite Environment API는 Nuxt 5에서 항상 활성화됩니다. `experimental.viteEnvironmentApi` 옵션은 제거되었습니다.
::

**주요 변경 사항:**

1. **환경별 `extendViteConfig()` 지원 중단**: `extendViteConfig()`의 `server` 및 `client` 옵션은 지원 중단되었으며 사용 시 경고가 표시됩니다.

2. **플러그인 등록 방식 변경**: `addVitePlugin()`으로 등록되고 하나의 환경만 대상으로 하는 Vite 플러그인(`server: false` 또는 `client: false` 전달)은 `config` 또는 `configResolved` 훅이 호출되지 않습니다.

3. **공유 설정**: `vite:extendConfig`와 `vite:configResolved` 훅은 이제 분리된 클라이언트/서버 설정이 아니라 공유 설정과 함께 동작합니다.

#### 변경 이유 %{#reasons-for-change}%

Vite Environment API는 다음을 제공합니다:
- 개발 빌드와 프로덕션 빌드 간 더 나은 일관성
- 환경별 설정에 대한 더 세밀한 제어
- 향상된 성능과 플러그인 아키텍처
- 클라이언트와 서버를 넘어서는 사용자 정의 환경 지원

#### 마이그레이션 단계 %{#migration-steps}%

##### 1. Vite 플러그인 사용으로 마이그레이션 %{#1-migrate-to-use-vite-plugins}%

`extendViteConfig`, `vite:configResolved`, `vite:extendConfig` 대신 Vite 플러그인을 사용하는 것을 권장합니다.

```ts
// 이전
extendViteConfig((config) => {
  config.optimizeDeps.include.push('my-package')
}, { server: false })

nuxt.hook('vite:extendConfig' /* or vite:configResolved */, (config, { isClient }) => {
  if (isClient) {
    config.optimizeDeps.include.push('my-package')
  }
})

// 이후
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // 여기에서 전역 vite 설정을 지정할 수 있습니다
  },
  configResolved (config) {
    // 여기에서 완전히 resolve된 vite 설정에 접근할 수 있습니다
  },
  configEnvironment (name, config) {
    // 여기에서 환경별 vite 설정을 지정할 수 있습니다
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

##### 2. Vite 플러그인을 환경 기반 방식으로 마이그레이션 %{#2-migrate-vite-plugins-to-use-environments}%

`addVitePlugin`에 `server: false` 또는 `client: false`를 사용하는 대신, 플러그인 내부에서 새로운 `applyToEnvironment` 훅을 사용할 수 있습니다.

```ts
// 이전
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    config.optimizeDeps.include.push('my-package')
  },
}), { client: false })

// 이후
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // 여기에서 전역 vite 설정을 지정할 수 있습니다
  },
  configResolved (config) {
    // 여기에서 완전히 resolve된 vite 설정에 접근할 수 있습니다
  },
  configEnvironment (name, config) {
    // 여기에서 환경별 vite 설정을 지정할 수 있습니다
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

### Vite 8로 마이그레이션 %{#migration-to-vite-8}%

🚦 **영향도**: 중간

#### 무엇이 바뀌었나 %{#what-changed}%

Nuxt 5는 Vite 7에서 [Vite 8](https://main.vite.dev/guide/migration)으로 업그레이드되며, 여기서는 esbuild와 Rollup 대신 [Rolldown](https://rolldown.rs)이 기반 번들러로 사용됩니다. 이로 인해 빌드 속도는 크게 빨라지지만 몇 가지 브레이킹 체인지도 함께 포함됩니다.

::note
Vite Environment API 마이그레이션과 달리, 이 변경 사항은 `future.compatibilityVersion: 5`로 미리 opt-in할 수 없습니다. Vite 8 호환성을 미리 테스트하고 싶다면 `package.json`에 `"vite": "^8.0.0-beta.15"` resolution override를 추가할 수 있습니다.
::

대부분의 마이그레이션은 Nuxt 내부에서 처리되지만, 사용자가 알아야 할 변경 사항도 일부 있습니다:

- **`vite.esbuild`와 `vite.optimizeDeps.esbuildOptions`**는 `vite.oxc`와 `vite.optimizeDeps.rolldownOptions` 사용을 위해 지원 중단되었습니다. Vite 8은 현재 이들을 자동 변환하지만 향후 제거될 예정입니다.
- **`build.rollupOptions`**는 `build.rolldownOptions` 사용을 위해 지원 중단되었습니다.
- **CommonJS interop 동작**이 변경되었습니다. CJS 모듈을 import한다면 자세한 내용은 [Vite 8 마이그레이션 가이드](https://main.vite.dev/guide/migration#consistent-commonjs-interop)를 확인하세요.

::read-more{to="https://main.vite.dev/guide/migration" target="_blank"}
모든 브레이킹 체인지와 마이그레이션 단계는 전체 Vite 8 마이그레이션 가이드를 참고하세요.
::

### Nitro v3로 마이그레이션 %{#migration-to-nitro-v3}%

🚦 **영향도**: 큼

#### 무엇이 바뀌었나 %{#what-changed}%

Nuxt 5는 서버 엔진을 대폭 다시 쓴 [Nitro v3](https://nitro.build/blog/v3-beta)로 업그레이드됩니다. Nitro v3는 [srvx](https://srvx.h3.dev)와 [h3 v2](https://h3.dev)를 기반으로 하며, 전반적으로 웹 표준 `Request`/`Response` API를 채택합니다. 이는 성능 향상과 더 일관된 API를 제공하지만, 서버 측 코드에는 여러 브레이킹 체인지가 포함됩니다.

::important
현재도 Nitro v3 통합 작업을 진행 중이므로, 추가 변경 사항과 더 쉬운 마이그레이션을 위한 후속 작업이 있을 수 있습니다.
::

::read-more{to="https://nitro.build/blog/v3-beta" target="_blank"}
전체 개요는 Nitro v3 베타 발표 글을 읽어보세요.
::

::read-more{to="https://nitro.build/docs/migration" target="_blank"}
모든 브레이킹 체인지는 전체 Nitro v3 마이그레이션 가이드를 참고하세요.
::

아래 섹션은 Nuxt 애플리케이션 개발자와 모듈 작성자에게 가장 관련 있는 변경 사항을 강조합니다.

#### 패키지와 import 경로 변경 %{#package-and-import-path-changes}%

`nitropack` 패키지 이름이 `nitro`로 변경되었습니다. 모든 import 경로도 바뀌었습니다:

| Before | After |
|---|---|
| `nitropack` | `nitro` |
| `nitropack/types` | `nitro/types` |
| `nitropack/runtime` | `nitro` |
| `h3` (for server utilities) | `nitro/h3` |

서버 라우트 내부의 auto-import(`defineEventHandler`, `getQuery`, `readBody`, `useRuntimeConfig` 등)은 변경 없이 계속 동작합니다.

서버 코드에 명시적 import가 있다면 다음처럼 업데이트하세요:

```diff
- import { defineEventHandler, getQuery } from 'h3'
+ import { defineEventHandler, getQuery } from 'nitro/h3'
```

**모듈 작성자**는 타입 확장이 새 모듈 경로를 가리켜야 합니다:

```diff
- declare module 'nitropack/types' {
+ declare module 'nitro/types' {
    interface NitroRouteRules {
      myModule?: { /* ... */ }
    }
  }
```

#### 오류 처리: `status`/`statusText`가 `statusCode`/`statusMessage`를 대체 %{#error-handling-status-statustext-replace-statuscode-statusmessage}%

h3 v2는 웹 표준에 맞추기 위해 오류 속성 이름을 변경했습니다:

```diff
  createError({
-   statusCode: 404,
-   statusMessage: 'Not Found',
+   status: 404,
+   statusText: 'Not Found',
  })
```

서버 라우트에서 오류 클래스는 이제 `HTTPError`이며 (`h3`의 `createError` 대체):

```diff
- import { createError } from 'h3'
+ import { HTTPError } from 'nitro/h3'

  export default defineEventHandler(() => {
-   throw createError({ statusCode: 400, statusMessage: 'Bad request' })
+   throw new HTTPError({ status: 400, statusText: 'Bad request' })
  })
```

::note
앱의 Vue 영역(`app/` 디렉터리)에서는 Nuxt의 `createError` 컴포저블이 계속 동작하며, 오류를 throw하는 권장 방식입니다.
::

#### 서버 Event API 변경 사항 (h3 v2) %{#server-event-api-changes-h3-v2}%

이제 `H3Event` 객체는 웹 표준 API를 사용합니다:

**Request 속성:**
```diff
- event.path              // string
+ event.url.pathname      // URL 객체 - .pathname, .search, .hash 사용

- event.method            // string
+ event.req.method        // via Web Request object

- event.node.req.headers  // Node.js IncomingHttpHeaders
+ event.req.headers       // Web Headers API (.get(), .set(), .has())
```

**Response 속성:**
```diff
- event.node.res.statusCode = 200
+ event.res.status = 200

- event.node.res.statusMessage = 'OK'
+ event.res.statusText = 'OK'

- setResponseHeader(event, 'x-custom', 'value')
+ event.res.headers.set('x-custom', 'value')

- appendResponseHeader(event, 'set-cookie', cookie)
+ event.res.headers.append('set-cookie', cookie)
```

#### `useRuntimeConfig()`는 더 이상 `event`를 받지 않음 %{#useruntimeconfig-no-longer-accepts-event}%

Nitro v3에서는 서버 라우트에서 `useRuntimeConfig()`가 더 이상 `event` 인자를 필요로 하지 않으며(또한 받지도 않습니다):

```diff
  export default defineEventHandler((event) => {
-   const config = useRuntimeConfig(event)
+   const config = useRuntimeConfig()
  })
```

#### Route Rules: `statusCode`가 `status`로 변경 %{#route-rules-statuscode-renamed-to-status}%

리디렉션 route rules를 정의한다면 속성 이름이 변경되었습니다:

```diff
  export default defineNuxtConfig({
    routeRules: {
      '/old-page': {
-       redirect: { to: '/new-page', statusCode: 302 },
+       redirect: { to: '/new-page', status: 302 },
      },
    },
  })
```

#### 모듈 작성자를 위한 추가 변경 사항 %{#for-module-authors-additional-changes}%

- **Nitro 플러그인 import**: 명시적 import에는 `import { definePlugin } from 'nitro'`를 사용하세요(auto-import는 계속 동작합니다).
- **런타임 훅**: `nitroApp.hooks.hook('beforeResponse', ...)`와 `nitroApp.hooks.hook('afterResponse', ...)`는 `nitroApp.hooks.hook('response', ...)`로 대체되었습니다.
- **`nitro/app`의 `getRouteRules()`**: 서버에서는 Nitro 헬퍼가 `getRouteRules(event)`에서 `getRouteRules(method, pathname)`으로 변경되었으며 `{ routeRules }`를 반환합니다.

### `experimental.externalVue` 제거 %{#removal-of-experimental-externalvue}%

🚦 **영향도**: 최소

#### 무엇이 바뀌었나 %{#what-changed}%

`experimental.externalVue` 옵션이 제거되었습니다. Vue 컴파일러 의존성(`@babel/parser`, `@vue/compiler-core`, `@vue/compiler-dom`, `@vue/compiler-ssr`, `estree-walker`)은 이제 `vue.runtimeCompiler`가 활성화되지 않은 경우 서버 번들에서 항상 mock 프록시로 대체됩니다.

#### 변경 이유 %{#reasons-for-change}%

Nitro v3로 마이그레이션하면서 모든 의존성이 기본적으로 서버 출력물에 번들됩니다(`node_modules`를 externalize했던 Nitro v2와 다름). `externalVue` 옵션은 원래 Vue를 외부 의존성으로 유지해 Vue의 여러 복사본이 함께 번들되지 않도록 하기 위해 설계되었지만, Nitro v3는 어차피 모든 것을 번들하므로 이 옵션은 아무 효과가 없게 되었습니다.

Vue의 서버 빌드에는 전체 컴파일러 툴체인이 포함되어 있어 `@babel/parser`(465KB)와 기타 컴파일러 패키지가 불필요하게 서버 번들에 포함됩니다. 이런 컴파일러 패키지는 런타임 템플릿 컴파일을 위해 `vue.runtimeCompiler`가 활성화된 경우에만 필요합니다.

이 컴파일러 의존성을 항상 mock 처리함으로써 기본 서버 번들 크기가 약 860KB(~59%) 줄어듭니다.

#### 마이그레이션 단계 %{#migration-steps}%

이전에 `experimental.externalVue`를 명시적으로 설정했다면 이제 제거해야 합니다.

```diff
  export default defineNuxtConfig({
    experimental: {
-     externalVue: false,
    },
  })
```

::note
`vue.runtimeCompiler: true`를 사용한다면 실제 컴파일러 패키지는 이전과 같이 계속 포함됩니다.
::

### `@vitejs/plugin-vue-jsx`는 이제 선택 사항 %{#vitejs-plugin-vue-jsx-is-now-optional}%

🚦 **영향도**: 최소

#### 무엇이 바뀌었나 %{#what-changed}%

`@vitejs/plugin-vue-jsx`는 더 이상 `@nuxt/vite-builder`와 함께 기본 설치되지 않습니다. 이제 이 패키지는 빌드 중 `.jsx` 또는 `.tsx` 파일이 발견될 때만 필요 시 로드되는 선택적 peer dependency입니다.

프로젝트에서 JSX/TSX 컴포넌트를 사용한다면 Nuxt가 이를 자동 감지하고 패키지 설치를 안내합니다.

#### 변경 이유 %{#reasons-for-change}%

`@vitejs/plugin-vue-jsx` 플러그인은 JSX를 사용하지 않는 프로젝트에는 불필요한 큰 의존성 트리(Babel, `@vue/babel-plugin-jsx` 등)를 끌어옵니다. 이를 선택 사항으로 바꾸면 대부분의 Nuxt 프로젝트에서 기본 설치 크기를 줄이고 의존성 해석 속도를 높일 수 있습니다.

#### 마이그레이션 단계 %{#migration-steps}%

프로젝트에서 `.jsx` 또는 `.tsx` 파일을 사용한다면 `@vitejs/plugin-vue-jsx`를 dev dependency로 추가하세요:

::code-group{sync="pm"}

```bash [npm]
npm install -D @vitejs/plugin-vue-jsx
```

```bash [yarn]
yarn add -D @vitejs/plugin-vue-jsx
```

```bash [pnpm]
pnpm add -D @vitejs/plugin-vue-jsx
```

```bash [bun]
bun add -D @vitejs/plugin-vue-jsx
```

::

또는 개발 중 JSX/TSX 파일이 처음 처리될 때 Nuxt가 자동 설치를 안내합니다.

프로젝트에서 JSX를 사용하지 않는다면 변경할 필요가 없습니다.

### 레거시 `_renderResponse` 지원 제거 %{#removal-of-legacy-renderresponse-support}%

🚦 **영향도**: 최소

#### 무엇이 바뀌었나 %{#what-changed}%

더 이상 `ssrContext._renderResponse`를 폴백으로 검사하지 않습니다. 내부 `ssrContext['~renderResponse']`(Nuxt 자체 router 컴포저블이 설정함)만 사용합니다.

#### 변경 이유 %{#reasons-for-change}%

`ssrContext`의 `_renderResponse` 속성은 [#33896](https://github.com/nuxt/nuxt/pull/33896)에서 내부 API를 `~renderResponse`로 마이그레이션한 이후 하위 호환용 폴백으로 남겨져 있었습니다. TODO 주석에는 Nuxt v5에서 제거해야 한다고 표시되어 있었습니다.

#### 마이그레이션 단계 %{#migration-steps}%

직접 `ssrContext._renderResponse`를 설정하고 있었다면(원래 공개 API는 아니었습니다), 대신 `ssrContext['~renderResponse']`를 사용하세요. Nuxt router 컴포저블은 이미 새 속성을 사용하므로 `navigateTo`나 route middleware를 통해 처리한다면 변경할 필요가 없습니다.

### 비동기 아님 `callHook` %{#non-async-callhook}%

🚦 **영향도**: 최소

#### 무엇이 바뀌었나 %{#what-changed}%

[hookable v6](https://github.com/unjs/hookable)로 업그레이드되면서, 이제 `callHook`는 항상 `Promise<void>`를 반환하는 대신 `void`를 반환할 수 있습니다. 이는 등록된 훅이 없거나 모든 훅이 동기식일 때 불필요한 `Promise` 할당을 피할 수 있게 해주는 큰 성능 개선입니다.

기본값(`compatibilityVersion: 4`)에서는 Nuxt가 기존 `.then()` 및 `.catch()` 체인이 계속 동작하도록 `callHook`를 `Promise.resolve()`로 감쌉니다. `compatibilityVersion: 5`에서는 이 래퍼가 제거됩니다.

::tip
이 변경은 빌드 시점 Nuxt 훅(Nuxt 모듈에서 사용)과 런타임 Nuxt 훅(애플리케이션 코드에서 사용할 수 있음) 모두에 영향을 줍니다.
::

#### 변경 이유 %{#reasons-for-change}%

Hookable v6의 `callHook`는 필요하지 않을 때 `Promise`를 만들지 않으므로 20~40배 더 빠릅니다. 이는 훅 호출 지점이 많은 애플리케이션에 이점이 됩니다.

#### 마이그레이션 단계 %{#migration-steps}%

당신이나 모듈이 `.then()` 또는 `.catch()` 체인과 함께 `callHook`를 사용하고 있다면 `await`로 전환하세요:

```diff
- nuxtApp.callHook('my:hook', data).then(() => { ... })
+ await nuxtApp.callHook('my:hook', data)
```

```diff
- nuxtApp.hooks.callHook('my:hook', data).catch(err => { ... })
+ try { await nuxtApp.hooks.callHook('my:hook', data) } catch (err) { ... }
```

::tip
`future.compatibilityVersion: 5`를 설정하거나([Nuxt 5 테스트](/docs/4.x/getting-started/upgrade#testing-nuxt-5) 참고) `experimental.asyncCallHook: false`를 명시적으로 활성화해 이 기능을 미리 시험할 수 있습니다.
::

또는 다음과 같이 설정해 `callHook`가 항상 `Promise`를 반환하게 만들 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    asyncCallHook: true,
  },
})
```

### 클라이언트 전용 주석 플레이스홀더 %{#client-only-comment-placeholders}%

🚦 **영향도**: 최소

#### 무엇이 바뀌었나 %{#what-changed}%

`compatibilityVersion: 5`에서는 클라이언트 전용 컴포넌트(`.client.vue` 파일과 `createClientOnly()` 래퍼)가 이제 서버에서 빈 `<div>` 요소 대신 HTML 주석(`<!--placeholder-->`)을 렌더링합니다.

#### 변경 이유 %{#reasons-for-change}%

플레이스홀더 `<div>`와 실제 컴포넌트 루트가 같은 태그 이름을 공유하면, Vue 런타임은 hydration 중 `setScopeId`를 다시 적용하지 않습니다. 이로 인해 컴포넌트가 마운트된 뒤 scoped styles가 누락됩니다. 주석 노드를 사용하면 태그 이름 충돌을 완전히 피할 수 있습니다.

#### 마이그레이션 단계 %{#migration-steps}%

레이아웃 목적(예: 레이아웃 시프트 방지를 위한 공간 확보)으로 플레이스홀더 `<div>`가 속성(`class`, `style` 등)을 상속하는 데 의존하고 있다면, 대신 `#fallback` 슬롯과 함께 `<ClientOnly>`로 컴포넌트를 감싸세요:

```diff
- <MyComponent class="placeholder" style="min-height: 200px" />
+ <ClientOnly>
+   <MyComponent />
+   <template #fallback>
+     <div class="placeholder" style="min-height: 200px"></div>
+   </template>
+ </ClientOnly>
```

::tip
`future.compatibilityVersion: 5`를 설정하거나([Nuxt 5 테스트](/docs/4.x/getting-started/upgrade#testing-nuxt-5) 참고) `experimental.clientNodePlaceholder: true`를 명시적으로 활성화해 이 기능을 미리 시험할 수 있습니다.
::

또는 다음과 같이 설정해 이전 `<div>` 플레이스홀더 동작으로 되돌릴 수 있습니다:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    clientNodePlaceholder: false,
  },
})
```
