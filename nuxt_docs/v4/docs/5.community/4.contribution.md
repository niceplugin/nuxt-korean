Nuxt 생태계에 기여할 수 있는 방법은 다양합니다.

## 생태계 %{#ecosystem}%

Nuxt 생태계에는 다양한 프로젝트와 조직이 포함됩니다:

* [nuxt/](https://github.com/nuxt) - Nuxt 프레임워크 자체의 핵심 저장소입니다. [**nuxt/nuxt**](https://github.com/nuxt/nuxt)에는 Nuxt 프레임워크(2와 3 모두)가 들어 있습니다.
* [nuxt-modules/](https://github.com/nuxt-modules) - 커뮤니티가 기여하고 유지 관리하는 모듈과 라이브러리입니다. 모듈을 `nuxt-modules`로 [이관하는 절차](/docs/4.x/guide/modules/ecosystem)가 있습니다. 이 모듈들은 각각의 유지 관리자가 있지만 특정 한 사람에게 의존하지는 않습니다.
* [unjs/](https://github.com/unjs) - 이 라이브러리들 중 다수는 Nuxt 생태계 전반에서 사용됩니다. 이들은 프레임워크 및 환경에 구애받지 않는 범용 라이브러리로 설계되었습니다. 다른 프레임워크와 프로젝트의 기여와 사용도 환영합니다.

## 기여하는 방법 %{#how-to-contribute}%

### 이슈 분류와 토론 지원 %{#triage-issues-and-help-out-in-discussions}%

돕고 싶은 프로젝트의 이슈와 토론을 살펴보세요. 예를 들어 Nuxt에는 [issues board](https://github.com/nuxt/nuxt/issues)와 [discussions](https://github.com/nuxt/nuxt/discussions)가 있습니다. 다른 사용자를 돕고, 우회책을 공유하고, 재현 예제를 만들고, 버그를 조금 파보고 발견한 내용을 공유하는 것만으로도 큰 차이를 만듭니다.

### 이슈 만들기 %{#creating-an-issue}%

이슈를 만드는 데 시간을 내 주셔서 감사합니다! ❤️

* **버그 신고**: 이슈를 열기 전에 해야 할 일은 [가이드](/docs/4.x/community/reporting-bugs)를 확인하세요.

* **기능 요청**: 생각 중인 기능 범위를 이미 다루는 기존 이슈나 discussion이 없는지 확인하세요. 해당 기능이 Nuxt 생태계의 다른 부분(예: 모듈)에 대한 것이라면 먼저 그곳에 기능 요청을 올리는 것을 고려해 주세요. 떠올린 기능이 일반적인 것이거나 API가 아직 완전히 명확하지 않다면, 먼저 **Ideas** 섹션에서 discussion을 열어 커뮤니티와 논의해 보세요.

이슈에 응답할 때는 [내부 이슈 의사결정 플로우차트](https://mermaid.live/view#pako:eNqFlE1v2zAMhv8K4UuToslhx2Bo0TZt12Edhm7YMCAXWqJtorLk6qOpkfS_j7KdfpyWQ-BQr8mHL6nsCuU0FauiMm6rGvQRfq03FuRzvvvTYIQHthpcBT_ugQNwPHuZjheLxf4i1VDx8x4udrf5EBCOQvSsYg4ffS79KS9pmX9QALTgyid2KYB7Ih-4bmKWbDk2YB0E1gRUVaRi-FDmmjAmT3u4nB3DmoNKIUA1BsGSohA49jnVMQhHbDh_EZQUImyxh-gAtfaiG-KWSJ-N8nt6YtpCdgEeE5rXPOdav5YwWJIJU7zrvNADV9C7JBIyIC07Wxupkx3LFQ5vCkguRno5f9fP2qnUko0Y2dk9rGdvHAa9IIhVGlCp5FFNPN-ce4DKeXBd53xMliOLp9IZtyORQVsnrGm-WJzejtUu5fFqdr5FGQ3bLslYvGthjZbJTLpReZG5_lLYw7XQ_CbPVT92ws9gnEJj-v84dk-PiaXnmF1XGAaPsOsMKywNvYmG80ZohV8k4wDR9_N3KN_dHm5mh1lnkM5FsYzRfNiTvJoT5gnQsl6uxjqXLhkNQ9syHJ0UZZ8ERUIlNShr6N8gZDEliR-ow7QZa0fhY4LoHLRo-8N7ZxPwjRj5ZZYXpvOSNs9v3Jjs8NXB4ets92xan3zydXZHvj64lKMayh4-gZC1bjASW2ipLeWuzIuToiXfImu5rbucclMIc0ubYiWPGv3DptjYF9Fhiu5nb1Wxij7RSZE6jZHWjLXHtlhVaIJESXN0_m68_sO_wMs_oO9gyg)를 따르도록 최선을 다하겠습니다.

### Pull Request 보내기 %{#send-a-pull-request}%

Pull request는 언제나 환영합니다! ❤️

#### 시작하기 전에 %{#before-you-start}%

버그를 수정하기 전에, **이를 설명하는 이슈가 있는지** 확인하는 것을 권장합니다. 문서 문제일 수도 있고, 알아두면 도움이 되는 맥락이 있을 수도 있기 때문입니다.

기능 작업을 하고 있다면 먼저 **feature request issue를 열어** 해당 기능이 필요한지, 그리고 기능 설계가 어떤지 유지 관리자와 논의해 주세요. 이렇게 하면 유지 관리자와 기여자 모두의 시간을 절약할 수 있고 기능도 더 빨리 출시할 수 있습니다. pull request에서 기능 구현을 시작하기 전에 그 이슈는 프레임워크 팀 구성원에게 **확인되어야 합니다**.

오타 수정은 더 깔끔한 커밋 이력을 유지하기 위해 여러 오타 수정을 하나의 pull request로 묶는 것이 좋습니다.

Nuxt 자체에 대한 더 큰 변경이라면 먼저 [Nuxt module을 만들고](/docs/4.x/community/contribution#create-a-module) այնտեղ 기능을 구현하는 것을 권장합니다. 이렇게 하면 빠른 proof-of-concept가 가능합니다. 그 다음 discussion 형태로 [RFC를 만들 수 있습니다](/docs/4.x/community/contribution#make-an-rfc). 사용자가 이를 채택하고 피드백을 모으면, 이를 다듬어 Nuxt core에 추가하거나 독립 모듈로 계속 유지할 수 있습니다.

#### 커밋 규칙 %{#commit-conventions}%

커밋 메시지에는 [Conventional Commits](https://www.conventionalcommits.org)를 사용하며, 이를 통해 커밋 기반으로 [changelog를 자동 생성](https://github.com/unjs/changelogen)할 수 있습니다. 아직 익숙하지 않다면 가이드를 읽어 주세요.

`fix:`와 `feat:`는 **실제 코드 변경**(로직에 영향을 줄 수 있는 경우)에 사용된다는 점에 유의하세요. 오타나 문서 변경에는 대신 `docs:` 또는 `chore:`를 사용하세요:

* ~~`fix: typo`~~ -> `docs: fix typo`

`nuxt/nuxt`처럼 모노레포 프로젝트에서 작업하는 경우, 커밋의 주요 범위를 괄호 안에 명시해야 합니다. 예: `feat(kit): add 'addMagicStuff' utility`.

#### Pull Request 만들기 %{#making-the-pull-request}%

pull request를 보내는 방법을 모른다면 [가이드](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-a-pull-request)를 읽는 것을 권장합니다.

pull request를 보낼 때는 PR 제목도 [Commit Convention](/docs/4.x/community/contribution#commit-conventions)을 따르는지 확인하세요.

PR이 기존 이슈를 수정하거나 해결한다면 PR 설명에 반드시 언급해 주세요.

하나의 PR에 여러 커밋이 있어도 괜찮습니다. 병합할 때 `Squash and Merge`를 사용해 커밋을 하나로 합치므로 변경 사항 때문에 rebase나 force push를 할 필요는 없습니다.

빠른 커밋을 위해 별도의 commit hook은 추가하지 않습니다. 하지만 pull request를 만들기 전에는 lint/test 스크립트가 모두 통과하는지 확인해야 합니다.

일반적으로 PR에 _관련 없는_ 변경이 없도록 해 주세요. 예를 들어 편집기가 수정한 파일의 다른 부분에 공백이나 서식 변경을 만들었다면, PR 변경 사항이 더 명확히 보이도록 이를 되돌려 주세요. 또한 하나의 PR에 여러 관련 없는 기능이나 수정을 포함하지 않도록 해 주세요. 분리할 수 있다면 여러 PR로 나누어 각각 검토하고 병합하는 편이 더 좋습니다. 일반적으로 PR은 _한 가지 일만_ 해야 합니다.

#### Pull Request를 만든 후 %{#once-you-ve-made-a-pull-request}%

pull request를 만들면 가능한 한 빠르게 검토하도록 최선을 다하겠습니다.

유지 관리자에게 할당되었다면, 그 사람이 특별히 주의를 기울여 검토하고 필요할 수 있는 변경 사항도 반영한다는 뜻입니다.

PR에 변경 요청이 달려도 빨간 글씨는 신경 쓰지 마세요! 그 PR이 나쁘다고 생각한다는 뜻이 아니라, pull request 목록 상태를 한눈에 쉽게 구분하기 위한 방식일 뿐입니다.

PR에 'pending' 표시를 하면, PR을 검토하는 데 우리가 해야 할 다른 작업이 남아 있다는 의미일 가능성이 높습니다. 이는 내부 메모일 뿐이며 PR이 좋은 아이디어인지 아닌지에 대한 평가를 뜻하지는 않습니다. pending 상태의 이유는 댓글로 설명하도록 최선을 다하겠습니다.

pull request에 응답하고 검토할 때는 [PR 의사결정 플로우차트](https://mermaid.live/view#pako:eNp9VE1v2kAQ_SsjXzBSEqlALlaUisSh0ACK2l4qcVm8Y9hi7672Iwly-O-ZtYPt5FAOCHbee_PmzdpVlCmOURLlhXrJ9sw4-JNuJNBnWs1UQafIQVjrERyWumAOv58-AJeXt29_0b7BXbWwwL0uRPa1vlZvcB_fF8oiMMmB2QM4BXkt3UoON7Lh3LWaDz2SVkK6QGt7DHvw0CKt5sxCKaQoWQEGtVHcZ04oGdw04LTVngW_LHOeFcURGGz97mw6PSv-iJdsi0UCA4nI7SfNwc3W3JZit3eQ1SZFDlKB15yswQ2MgbOjbYeatY3n8bcr-IWlekYYaJRcyB04I9gOB1CEfkF5dAVTzmFAtnqn4-bUYAiMMmHZgWhNPRhgus5mW2BATxq0NkIZ4Y4NbNjzE2ZchBzcHmGLe_ZMSKCcyRXyLrVFa_5n_PBK2xKy3kk9eOjULUdltk6C8kI-7NFDr8f4EVGDoqlp-wa4sJm3ltIMIuZ_mTQXJyTSkQZtunPqsKxShV9GKdkBYe1fHXjpbcjlvONlO9Kqx_M7YHmOmav_luxfE5zKwVs09hM5DLSupgYDlr5flDkwo7ykixKG-xDsUly1LZ-uY32dgDc7lG7YqwbNp0msJwmIUivjWFtfd-xRrEcJ7Omydz37qFplHOtxEp4GskI2qB5dRCWakglOz3oV8JuITJa4iRL6yZk5bKKNPBGOead-H2UWJc54vIiaW53SPgwrz4fIhVNm1bw76lfI6R2_MW21)를 따르도록 최선을 다하겠습니다.

### AI 지원 기여 %{#ai-assisted-contributions}%

Nuxt에 기여할 때 AI 도구를 신중하게 사용하는 것은 환영하지만, 모든 기여자는 [두 가지 핵심 원칙](https://roe.dev/blog/using-ai-in-open-source)을 따라 주시길 바랍니다.

#### LLM이 당신을 대신해 말하게 두지 마세요 %{#never-let-an-llm-speak-for-you}%

* 모든 댓글, 이슈, pull request 설명은 자신의 목소리로 작성해야 합니다
* 완벽한 문법이나 맞춤법보다 명확하고 인간적인 소통을 더 중요하게 생각합니다
* 자신의 이해를 반영하지 않는 AI 생성 요약문을 그대로 복사해 붙여넣지 마세요

#### LLM이 당신을 대신해 생각하게 두지 마세요 %{#never-let-an-llm-think-for-you}%

* 코드를 생성하거나 아이디어를 탐색하는 데 AI 도구를 자유롭게 사용할 수 있습니다
* 완전히 이해하고 설명할 수 있는 기여만 제출하세요
* 기여는 자신의 추론과 문제 해결을 반영해야 합니다

우리의 목표는 품질을 보장하고 실제 사람들과 협업하고 소통하는 즐거움을 유지하는 것입니다. Nuxt 커뮤니티의 AI 정책을 개선할 아이디어가 있다면 언제든 듣고 싶습니다! ❤️

### 모듈 만들기 %{#create-a-module}%

Nuxt로 멋진 것을 만들었다면 [모듈로 분리](/docs/4.x/guide/modules)해서 다른 사람과 공유해 보는 건 어떨까요? 이미 [훌륭한 모듈이 많이](/modules) 있지만, 더 많아질 여지는 언제나 있습니다.

만드는 동안 도움이 필요하면 언제든 [도움을 요청해 주세요](/docs/4.x/community/getting-help).

### RFC 만들기 %{#make-an-rfc}%

큰 새 기능을 시험하고 커뮤니티 채택을 얻기 위해 먼저 [모듈을 만드는 것](/docs/4.x/community/contribution#create-a-module)을 강력히 권장합니다.

이미 그렇게 했거나 새 모듈을 만드는 것이 적절하지 않다면, 먼저 새로운 discussion을 만들어 주세요. 자신의 생각이 최대한 명확하게 설명되어야 합니다. 새 API에 대해서는 코드 예시나 함수 시그니처를 포함하세요. 기존 이슈나 pain point도 예시와 함께 참조하세요.

이것이 RFC가 되어야 한다고 판단되면 카테고리를 RFC로 바꾸고 더 넓게 공유해 피드백을 받겠습니다.

RFC는 이후 다음 단계를 거칩니다:

* `rfc: active` - 현재 댓글을 받을 수 있는 상태
* `rfc: approved` - Nuxt 팀의 승인을 받은 상태
* `rfc: ready to implement` - 구현용 이슈가 생성되고 할당된 상태
* `rfc: shipped` - 구현된 상태
* `rfc: archived` - 승인되지는 않았지만 향후 참고를 위해 보관된 상태

### 생태계 전반의 규칙 %{#conventions-across-ecosystem}%

다음 규칙은 `nuxt/` 조직 내에서는 _필수_이며, 생태계의 다른 유지 관리자에게도 권장됩니다.

#### 모듈 규칙 %{#module-conventions}%

모듈은 [Nuxt module template](https://github.com/nuxt/starter/tree/module)를 따라야 합니다. 자세한 내용은 [module guide](/docs/4.x/guide/modules)를 참고하세요.

#### 핵심 `unjs/` 라이브러리 사용 %{#use-core-unjs-libraries}%

생태계 전반에서 사용되는 다음 라이브러리를 권장합니다:

* [pathe](https://github.com/unjs/pathe) - 범용 경로 유틸리티 (node `path` 대체재)
* [ufo](https://github.com/unjs/ufo) - URL 파싱 및 결합 유틸리티
* [obuild](https://github.com/unjs/obuild) - rolldown 기반 빌드 시스템
* ... 그 밖에도 더 많은 라이브러리는 [unjs/](https://github.com/unjs) 조직을 확인해 보세요!

#### ESM 구문 사용 및 `type: module` 기본 사용 %{#use-esm-syntax-and-default-to-type-module}%

Nuxt 생태계의 대부분은 ESM을 직접 소비할 수 있습니다. 일반적으로 우리는 `__dirname`, `require` 문 같은 CJS 전용 코드 사용을 피하는 것을 권장합니다. [ESM에 대해 더 읽어볼 수 있습니다](/docs/4.x/guide/concepts/esm).

#### Corepack이란 %{#what-s-corepack}%

[Corepack](https://github.com/nodejs/corepack)은 관련 명령을 실행할 때 올바른 패키지 관리자 버전을 사용하도록 보장합니다. 프로젝트는 `package.json`에 `packageManager` 필드를 가질 수 있습니다.

아래와 같은 구성을 가진 프로젝트에서는 Corepack이 `pnpm` `v7.5.0`을 설치하고(아직 없다면) 이를 사용해 명령을 실행합니다.

```jsonc [package.json]
{
  "packageManager": "pnpm@7.5.0"
}
```

#### ESLint 사용 %{#use-eslint}%

우리는 [`@nuxt/eslint`](https://github.com/nuxt/eslint)와 함께 [ESLint](https://eslint.org)를 린트와 포맷팅 모두에 사용합니다.

##### IDE 설정 %{#ide-setup}%

[VS Code](https://code.visualstudio.com)와 [ESLint extension](https://marketplace.visualstudio.com/items?itemName=dbaeumer.vscode-eslint)을 함께 사용하는 것을 권장합니다. 원한다면 편집 중인 코드를 저장할 때 자동 수정과 포맷팅을 활성화할 수 있습니다:

```json [settings.json]
{
  "editor.codeActionsOnSave": {
    "source.fixAll": "never",
    "source.fixAll.eslint": "explicit"
  }
}
```

#### Prettier 없음 %{#no-prettier}%

ESLint가 이미 코드 포맷팅에 맞게 구성되어 있으므로 Prettier로 기능을 중복할 필요는 없습니다. 코드를 포맷하려면 `yarn lint --fix`, `pnpm lint --fix`, `bun run lint --fix`, `deno run lint --fix`를 실행하거나 IDE 설정은 [ESLint section](/docs/4.x/community/contribution#use-eslint)을 참고하세요.

편집기에 Prettier가 설치되어 있다면 충돌을 피하기 위해 프로젝트 작업 시에는 비활성화하는 것을 권장합니다.

#### 패키지 관리자 %{#package-manager}%

모듈, 라이브러리, 앱의 패키지 관리자로 `pnpm`을 권장합니다.

프로젝트와 동일한 패키지 관리자 버전을 사용하도록 보장하기 위해 Corepack을 활성화하는 것이 중요합니다. Corepack은 매끄러운 패키지 관리자 통합을 위해 최신 node 버전에 내장되어 있습니다.

활성화하려면 다음을 실행하세요

```bash [Terminal]
corepack enable
```

이 작업은 컴퓨터에 Node.js를 설치한 뒤 한 번만 수행하면 됩니다.

## 문서 스타일 가이드 %{#documentation-style-guide}%

문서는 Nuxt의 핵심적인 부분입니다. 우리는 직관적인 프레임워크를 지향하며, 그 큰 부분은 생태계 전반에서 개발자 경험과 문서가 모두 훌륭하도록 만드는 것입니다. 👌

문서를 더 좋게 만드는 데 도움이 될 몇 가지 팁입니다:

* 가능하면 _simply_, _just_, _obviously..._ 같은 주관적인 단어는 피하세요.

  독자는 서로 다른 배경과 경험을 가질 수 있다는 점을 기억하세요. 따라서 이런 단어들은 의미를 잘 전달하지 못하고 해가 될 수 있습니다.
